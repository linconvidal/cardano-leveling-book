--- title: Events, hash chains and checkpoints map_title: Events and checkpoints summary: Link changes, detect rewrites and append corrections without erasing history. ---
Objectives
  1. Build three hash-linked events and locate a broken link.
  2. Compare a sequence with a checkpoint obtained from an independent source.
  3. Append a correction and distinguish the history from the current view.
Before you begin

Review bytes and hashes in Module 0, metadata in Lesson 1.9 and transaction queries in Lesson 1.11. The examples use only the Python available in this booklet, with no wallet or network submission.

Guiding question

If someone can recalculate all the hashes, what prevents them from presenting a different history?

1. The result changed, but the notification has already gone out

A system tracks test T-0142. It first creates the record as pending. It then records a passing result. Finally, it records that it sent a notification to the portal. The screen shows only aprovado (passed), but that word does not explain how the record got there.

An event records a declared change or action. The current view is calculated from events according to an application rule. In this example, creation, result and correction events can determine the displayed result; a notification does not change it. The three events are kept in an external file. We are not creating three Cardano transactions.

The seq field determines the order in which events are appended. The prev field contains the previous event's hash; the first uses null. An event's hash includes all its fields, including prev, but does not contain the hash itself.

2. Experiment: break and rewrite

We will fix a local recipe called guia.eventos.v1: JSON in UTF-8, sorted ASCII keys, no optional spaces, only the strings, integers and null used in this example, with no Unicode normalization. We prepend the ASCII prefix GUIA-EVENTO:v1 and a zero byte to the data bytes. We calculate SHA-256 over this sequence. The prefix identifies the use and version.

This limited recipe makes the demonstration reproducible; json.dumps with these options does not implement the full JCS from RFC 8785. An integration must specify an interoperable profile and test its edge cases, rather than copy the example for arbitrary JSON.

Run the code. The first comparison accepts the chain. The second detects the isolated edit. The third accepts the links in a complete rewrite, but the fourth rejects its head against the checkpoint saved beforehand. The Portuguese record keys and values are fixed hash inputs: tipo means type, registro record, resultado result and canal channel; criado, notificado, pendente, aprovado and reprovado mean created, notified, pending, passed and failed.

import hashlib
import json
from copy import deepcopy

def hash_event(event):
    data = json.dumps(event, sort_keys=True,
        ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(b"GUIA-EVENTO:v1\x00" + data).hexdigest()

def append_event(chain, fields):
    event = dict(fields, seq=len(chain) + 1,
        prev=hash_event(chain[-1]) if chain else None)
    return chain + [event]

def links_match(chain):
    previous = None
    for seq, event in enumerate(chain, 1):
        if event["seq"] != seq or event["prev"] != previous:
            return False
        previous = hash_event(event)
    return True

chain = []
for fields in [
    {"tipo": "criado", "registro": "T-0142", "resultado": "pendente"},
    {"tipo": "resultado", "resultado": "aprovado"},
    {"tipo": "notificado", "canal": "portal"},
]:
    chain = append_event(chain, fields)
checkpoint = (len(chain), hash_event(chain[-1]))
print("original:", links_match(chain))

edited = deepcopy(chain)
edited[1]["resultado"] = "reprovado"
print("isolated edit:", links_match(edited))
rewritten = []
for event in edited:
    rewritten = append_event(rewritten, event)
print("consistent rewrite:", links_match(rewritten))
print("same head:", hash_event(rewritten[-1]) == checkpoint[1])

Also change the result of the first event and run it again. The effect propagates through subsequent hashes. Removing the last event, however, leaves the remaining links consistent: without knowing which head to expect, the verifier may receive only an old prefix.

3. The checkpoint stays outside the presented history

A checkpoint associates a position with a head hash. In the experiment, we saved the pair before the edit. In a real system, it must arrive through a source that the chain's presenter cannot replace along with the events: a previously checked copy, a checkpoint signed by a trusted key or a publication located on the expected network.

Publishing the pair in a transaction lets us return to the observed commitment. We must check the expected publisher and inclusion; accepting any transaction with a different hash would allow the reference to be replaced. The network preserves the publication, but does not assess the test result.

A three-event checkpoint commits to that prefix. A chain with four events can preserve it. This does not show that the fourth is the latest, that no event went uncaptured or that all results are correct. To assess freshness, also obtain the latest head through the route defined for the record.

4. Correct by appending

Reviewing the source file reveals that the result should have been failed. The system appends event 4 with type correcao (correction), result reprovado (failed), a reason and two different links: prev points to event 3, while alvo (target) points to the hash of event 2. The first continues the chain; the second identifies the statement being corrected.

The view now shows failed and should allow the correction to be opened. The history still shows that there was a passing result and a notification. Appending a correction does not undo the notification or remove the need to inform its recipient.

If the correction declares ocorrido_em = 2026-09-10T10:00:00Z (occurred at) and its checkpoint was observed at 11:30, these times describe different things. The first was declared by the issuer; the second records when the publication was queried. Block and slot locate inclusion. None of them proves that the test took place at 10:00. Do not reorder the chain by the declared time to “fix” this difference.

Activity: accept the correction, reject the rewrite

The verifier below already checks the links, but forgets the checkpoint and ends with True. Fix its final check: reject a chain shorter than count and compare the hash at the committed position with head. Do not require the chain to end at that position, since corrections may have been appended. The contract accepts checkpoints with a positive count. In the fixed record data, motivo means reason and erro de leitura means reading error.

import hashlib
import json

def hash_event(event):
    data = json.dumps(event, sort_keys=True,
        ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(b"GUIA-EVENTO:v1\x00" + data).hexdigest()

def append_event(chain, fields):
    return chain + [dict(fields, seq=len(chain) + 1,
        prev=hash_event(chain[-1]) if chain else None)]

def verify(chain, count, head):
    previous = None
    for seq, event in enumerate(chain, 1):
        if event["seq"] != seq or event["prev"] != previous:
            return False
        previous = hash_event(event)
    return True

chain = []
for event_type in ["criado", "resultado", "notificado"]:
    chain = append_event(chain, {"tipo": event_type})
head = hash_event(chain[-1])
corrected = append_event(chain, {
    "tipo": "correcao", "alvo": hash_event(chain[1]),
    "resultado": "reprovado", "motivo": "erro de leitura",
})
print("prefix preserved:", verify(corrected, 3, head))
print("tail omitted:", verify(chain[:2], 3, head))
Check answer

Before the comparison, test len(chain) < count and return False in that case. Otherwise, the final check is hash_event(chain[count - 1]) == head. The subtraction converts the position counted from 1 into a Python index. The correct output is True for the appended correction and False for the omitted tail.

Comparing only the last hash would reject a legitimate extension. Accepting only the links would allow a consistent rewrite. We need both checks.

What we learned

  • The current view applies rules to events; it does not replace the history.
  • Links detect local inconsistencies. An independent checkpoint lets us compare the history with a known prefix.
  • A correction points to the previous head and separately identifies the corrected event.
  • The declared time, inclusion and observation of the publication are not the same instant.
