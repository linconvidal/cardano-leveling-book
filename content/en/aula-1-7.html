--- title: 'UTxO and eUTxO: outputs, spending and change' short_title: UTxO and eUTxO map_title: eUTxO summary: Understand the balance shown by a wallet, follow how outputs are consumed and recognize the role of the datum. ---
Objectives
  1. Relate a wallet's balance to the unspent outputs it queries.
  2. Identify an output and follow its consumption, the payment and the change.
  3. Distinguish the data associated with an output from the rule that authorizes spending it.
Before you begin

In Lesson 1.5, the address identified the spending conditions. In 1.6, we saw inputs and outputs in the transaction body. Now we will see what those inputs point to and what happens to the values when the transaction is accepted.

Guiding question

If you use a 7 ADA output to pay 5 ADA, where does the rest go?

1. The balance shown by the wallet

You open your wallet and see 11 ADA. That number may combine amounts received at different times: a 7 ADA output and a 4 ADA output, for example. The wallet queries the available outputs at its addresses and adds their values to display the balance.

Each of these outputs is a UTxO, short for Unspent Transaction Output: a transaction output that has not yet been spent. It was created by an earlier transaction and remains available for use in another.

Think of these outputs as banknotes, each with its own value. On Cardano, each “note” is also associated with an address that identifies the condition for spending it. The values do not have to follow fixed denominations like paper banknotes.

2. Which output will be spent, and who can spend it?

Knowing the balance is not enough to build a transaction. You need to identify the outputs that will be used as inputs. Each output is identified by the hash of the transaction that created it and its index in the output list, starting at zero.

To consume an output, the transaction must satisfy the condition identified by the payment credential. For a key credential, this requires the corresponding public key and a valid signature. For a script credential, spending must satisfy that script's rule. Copying the address or knowing the reference does not provide this authorization.

3. A payment consumes the entire output

Suppose Ana controls both outputs in the example and wants to pay Bruno 5 ADA. Assume a fee of 0.2 ADA for this transaction. The 7 ADA output is enough to cover both amounts; the 4 ADA output can remain unused.

The input references 8f3c2a91d6e4…#0. When the transaction is accepted, that 7 ADA output is consumed in full. The 5 ADA payment and the 1.8 ADA in change are new outputs, created by transaction c9047f2a61bd….

The change can return to Ana's same address, but it has a new reference: c9047f2a61bd…#1. The old 8f3c2a91d6e4…#0 remains in the history as a spent output and cannot be used again. The wallet now adds the untouched 4 ADA to the 1.8 ADA in change and shows 5.8 ADA.

If two transactions try to spend the same output, both can be prepared, but they cannot both complete that spend on the same chain. Once one consumes the output, the other must be rebuilt using inputs that are still available. This is why an application tracks the references used as well as the total balance.

In a simple ADA payment, the value of the inputs must cover the value of the outputs and the fee. Change must be included when building the transaction; it does not appear automatically in the ledger. The wallet or SDK usually handles this selection and calculation. A real transaction's fee and each output's minimum ADA depend on their data and the current parameters. In the next lesson, we will calculate the fee and set the transaction's validity interval.

4. What eUTxO adds

Besides transferring value, an application may need to store data that will be used to decide a future spend. The eUTxO, or extended UTxO, model retains the consumption and creation of outputs while expanding what a script rule can check.

These data are called a datum. An output can contain the datum or the hash that identifies it. In the latter case, the spender supplies the corresponding data when the script requires them.

The datum is not the spending rule. The rule is code: the script reads the data and checks the conditions specified for that transaction.

For example, the datum may record version = 3, while the script requires an update to create a new output with version = 4. The change happens by consuming the previous output and creating its successor, without editing the old output's datum. Which successors are required depends on the rule written in the script.

When spending, the transaction can also supply a redeemer, with information about the intended action. The script checks this action along with the datum and transaction context. We will work with these elements in Lesson 1.12; for now, the important distinction is between the data associated with the output and the code that decides whether it can be spent.

What we learned

  • The wallet calculates its balance from the unspent outputs associated with its addresses.
  • An input identifies the output by the hash of the transaction that created it and its index. The address identifies the spending condition.
  • The selected output is consumed in full. Payment and change have new references; unused outputs remain available.
  • In eUTxO, the datum supplies data associated with the output. The script contains the rule that uses those data to check a spend.
