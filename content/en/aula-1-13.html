Objectives
  1. Relate the User Token and Reference NFT by policy ID, CIP-67 label and base name.
  2. Interpret the datum wrapper without confusing the standard's version with the record's revision.
  3. Distinguish a reference input from normal spending and identify the limits of what a validator checks.
Before you begin

Review asset identity and CIP-25 in Lesson 1.10 and Plutus successor validation in Lesson 1.12. Here we apply these mechanisms to state discovered through a pair of assets.

Guiding question

How can a record's description be updated without taking the token that identifies it away from the user?

1. Two assets with different controls

Consider record REC-0042. Its user receives a token they can transfer. The application needs to update REC-0042's reference description when the report is revised. If the state depended on the user's output, every update would require consuming that output. The CIP-68 convention separates the transferable asset from the asset that identifies the reference state.

The User Token sits in the output controlled by the user. The Reference NFT identifies the output carrying the reference datum. Both belong to the same policy and have the same base name, but different prefixes in the asset name. They are two distinct assets; sharing a policy does not mean sharing a spending condition.

In this application, the User Token is an NFT with quantity 1 at a key address. The Reference NFT has quantity 1 and sits at a Plutus script address, with a validator that restricts updates. CIP-68 organizes representation and discovery; issuance security, Reference NFT uniqueness and spending rules depend on the chosen policies and scripts.

2. Labels are bytes in the asset name

CIP-67 defines a four-byte prefix encoding the label and checksum. The Reference NFT uses label 100; the User Token uses 222 for an NFT, 333 for a fungible token (FT) or 444 for a Rich Fungible Token (RFT). Do not write the digits “100” or “222” as text or put the label only in metadata: the prefix is part of the name's bytes.

RoleLabelCIP-67 prefix in hex
Reference NFT100000643b0
User Token NFT222000de140
User Token FT3330014df10
User Token RFT444001bc280

The base name REC-0042 has UTF-8 bytes 5245432d30303432. For the same policy, the full names are:

base = "REC-0042".encode("utf-8")
user = bytes.fromhex("000de140") + base
reference = bytes.fromhex("000643b0") + base
print("User Token:", user.hex())
print("Reference NFT:", reference.hex())
print("same names?", user == reference)
print("same base?", user[4:] == reference[4:])

The output shows different names and identical bases. The asset name's total limit of 32 bytes still applies, leaving at most 28 bytes for the base name. In production, validate the CIP-67 prefix, including its checksum, with a compatible tool. The complete prefixes in the table are enough to recognize the three types used in the exercise.

After validating the length and checking the first four bytes against the table, return bytes.fromhex("000643b0") + user_name[4:]. For REC-0042, the result is 000643b05245432d30303432. Looking up this name under another policy may find an asset unrelated to the user; both components determine the pair.

3. The datum contains a wrapper, not just a description

The Reference NFT's output stores an inline datum under CIP-32. CIP-68 defines a Plutus Data constructor 0 with three fields: [metadata, version, extra]. The first position is the metadata map; the second is the standard's representation version; the third contains additional Plutus Data. This metadata in the datum is visible to Plutus and must not be confused with transaction metadata in auxiliary data.

For the example's label-222 NFT, the direct metadata includes name and image. Our application adds record_version and artifact_hash. The hash below is abbreviated, and the utf8 notation only indicates text bytes; this block is not serialized CBOR. The fixed text Registro REC-0042 means “Record REC-0042”.

constructor 0 [
  {
    utf8("name"): utf8("Registro REC-0042"),
    utf8("image"): utf8("https://example.org/rec-0042.svg"),
    utf8("record_version"): 3,
    utf8("artifact_hash"): h'7c20...'
  },
  1,
  unit
]

The record's revision is 3; the wrapper version used here is 1. Updating the report to revision 4 does not automatically mean changing version to 4. The application must interpret the supported version before reading the other fields. Naming the application field record_version avoids confusing these counters.

4. Read by reference or consume to update

A reference input, defined in CIP-31, makes an output available to read without consuming it. Its value does not fund the transaction, and merely referencing it does not run its spending validator. A script reading this reference must check the Reference NFT's full identity and the data format; it must not trust just any datum found at the same address.

To update, the transaction uses the reference output as a normal input, satisfies its spending validator and creates a successor with the same Reference NFT and an updated datum. The rule must check authorization, token continuation and the permitted transition, as in the Plutus exercise. The User Token can stay where it was. If another transaction has already consumed the reference, the builder must query the active state and rebuild its attempt.

The old version remains in the history, but is no longer an available output. Reading a cached copy does not demonstrate that it is the current version; check the reference and whether it has been consumed. Changing the validator's code still requires migration accepted by the previous script.

Activity 2: the report has changed

REC-0042 moves from revision 3 to 4. The CIP-68 version remains compatible with 1. An application proposes only adding d42e8a1b6c90…#0 as a reference input and changing the datum in memory. Write down what is missing to make the update take effect.

Check answer

A reference input only reads. The update must consume d42e8a1b6c90…#0 as a normal input and create 0c7f92a6e4b1…#0 with the same Reference NFT under the expected spending condition, preserving wrapper version 1 and changing record_version to 4. The validator must accept this transition. Changing the application's memory does not change the ledger.

5. What the update does not verify

Even a correct validator only checks the implemented conditions over visible data. CIP-68 does not require the ledger to retrieve the image or report and does not prove their correctness. To check artifact_hash, obtain the original and use the same algorithm and byte representation defined for the record, as we studied in Lessons 0.1 and 0.2. Holding the User Token also does not prove delivery of the artifact, institutional authorization or access to the repository.

The CIP-68 pair is useful when the application needs this relationship between a transferable asset and state discovered by reference. Script state without a user token may suffice in another case; adopting the standard does not remove the need to define who can update, how the state is identified and how artifacts remain retrievable.

What we learned

  • CIP-68 relates two assets by policy and base name, with distinct CIP-67 labels.
  • The wrapper contains metadata, version and extra; the record's revision is a separate field.
  • A reference input reads without spending. Updating requires consumption and a successor under the applicable rule.
  • The standard organizes state and discovery without proving external content.
