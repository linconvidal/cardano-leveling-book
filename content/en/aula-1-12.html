Objectives
  1. Locate the state, requested action and observable effects in a spending attempt.
  2. Test a state-continuation rule without relying solely on the redeemer.
  3. Distinguish phase-1 and phase-2 failures and migration between script versions.
Before you begin

Review eUTxO in Lesson 1.7, fees and validity in Lesson 1.8 and native scripts in Lesson 1.10. You already know that a transaction proposes consuming outputs and creating others; now we will examine the rule that accepts or rejects that proposal.

Guiding question

The redeemer requests an “increment”. How can we prevent the transaction from creating a different version from the one requested?

1. A rule that needs to see the outputs

A record is at version 3 and must advance to exactly 4. Requiring two signatures before a deadline would fit a native script. Requiring the new output to preserve the record and contain the correct version needs access to the transaction's data and effects. This is one use of Plutus.

A Plutus spending validator runs when a transaction attempts to consume an output protected by its script credential. It is neither a continuously running service nor a function that changes the ledger from within. The builder proposes inputs and outputs; the script decides whether the attempt satisfies its conditions. The ledger applies the transition only under the relevant validation and inclusion rules.

Native scripts and Plutus are alternatives chosen according to the information needed. Plutus adds expressiveness and execution costs; it is not a mandatory step in every issuance or transfer. Languages such as Aiken, OpShin and plu-ts let you write these rules. Their compilers produce UPLC (Untyped Plutus Core) code, which the network evaluates. The program written by the developer and the code executed by the ledger are different representations; compiling without errors does not demonstrate that the rule is correct.

2. Datum, redeemer and context

The datum is the data associated with the protected state. It can appear directly in the output as an inline datum under CIP-32, or be committed to by a datum hash and supplied when needed. The redeemer is supplied in the candidate transaction: it states which action is being requested. The ScriptContext is built by the ledger and exposes transaction information relevant to the script's purpose.

Inputs, outputs, mint, the validity interval, signatories and reference inputs can inform the decision depending on the Plutus version and purpose. The exact form of the arguments varies between versions; separating state, request and context remains useful. The signatories visible to the script are not an arbitrary list of all witnesses: the builder must declare the relevant required signers in the body, and the ledger requires their signatures.

Transaction metadata is auxiliary data and does not appear in the ScriptContext. Putting approved: true in metadata does not give the validator a verifiable condition. Information needed by the rule must arrive through visible structures such as the datum, redeemer or outputs. The script also does not download a report from its URL; it checks the supplied data and the commitments defined in the application.

3. Check the output, not just the request

The example follows the continuation of a single record. The successors list contains all candidate outputs for that record. The rule requires exactly one, locked by the same script, with the same value and the previous version plus one. In a real application, the state must be identified unambiguously, for example by a unique token whose policy guarantees that uniqueness. Merely finding an output with the same name or datum does not authenticate the state's origin.

Activity 1: validate the continuation

The initial code checks only the redeemer. Fix continues to also check the number of successors, the script, the value and the version actually proposed. Keep the test data: the function must accept the correct update and reject the others. This is instructional Python, not a compilable validator or a complete transaction. The fixed data uses contador (“counter”), valor (“value”) and versao (“version”); the actions Incrementar and Encerrar mean “Increment” and “Close”.

def continues(previous, redeemer, successors):
    return redeemer == "Incrementar"

previous = {"script": "contador", "valor": 2, "versao": 3}
correct = {"script": "contador", "valor": 2, "versao": 4}
jump = {"script": "contador", "valor": 2, "versao": 7}
print("increment:", continues(previous, "Incrementar", [correct]))
print("jump:", continues(previous, "Incrementar", [jump]))
Check answer

First reject a redeemer other than Incrementar or a list whose length is not 1. Then compare the single successor: the script and value must match the previous ones, and versao == previous["versao"] + 1. The correct attempt passes; the jump to 7 fails. Preserving two fields does not compensate for violating the third. The builder must still satisfy the fee, accounting, state identification and other rules outside this example.

4. Phase-1 failure, phase-2 failure and collateral

Phase 1 checks conditions such as structure, available inputs, value conservation, key witnesses, native scripts and time validity. A failure in this phase rejects the transaction without executing the collection path for a Plutus failure. In phase 2, Plutus scripts are evaluated with CPU and memory budgets. A logically correct rule can still fail because of insufficient resources or incorrect assembly.

If Plutus evaluation succeeds and the transaction is included through the normal path, normal inputs are consumed and the proposed outputs are created. Collateral is not collected on that path. If a transaction passes phase 1 and is included marked as invalid in phase 2, the normal transition does not occur: the record's eUTxO remains available and normal outputs are not created. The ledger applies the collateral path separately.

Collateral inputs are explicit references to suitable UTxOs, not an abstract wallet balance. The net amount collectible must meet the current rules and parameters. Under rules with collateral return, the excess can return in its own output; any tokens present must be returned, since the net collection is in ADA. A simple selection uses ADA-only collateral. total_collateral, when present, must match the applicable difference. A failed local simulation does not automatically collect collateral: evaluation, submission and inclusion must be distinguished.

Outputs' minimum ADA depends on their size and the era's parameters; it is not universally 1 ADA. Use a compatible library and evaluate scripts before requesting a signature.

5. A new code version does not move the state

Changing the script's bytes changes its hash and the address credential. Publishing V2 or pointing the interface to another address does not transfer the outputs protected by V1. A migration must consume the old state through a transaction accepted by V1's rules and create state compatible with V2.

Plan this exit before locking value: the permitted destination, authorization, new datum format and asset preservation. Test the normal path, invalid attempts and migration, with auditing and monitoring proportionate to the risk. If V1 does not allow a suitable exit, that permission cannot be added retroactively just by publishing another script; the state may become locked in place.

What we learned

  • Plutus checks a candidate transaction using state, request and context.
  • The redeemer does not replace checking the effects in the outputs.
  • An invalid phase 2 does not apply the normal transition; collateral has a separate path.
  • Migrating state requires a transaction accepted by the script currently protecting it.
