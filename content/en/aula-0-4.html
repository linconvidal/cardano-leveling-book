Objectives
  1. Identify the inputs and outputs of signing and verification.
  2. Sign a message and observe how a change affects verification.
  3. Distinguish successful verification from confirmation of identity, truth or permission.
Before you begin

To follow this lesson, you need to know how to convert text to UTF-8 bytes and distinguish the private key from the public key.

Guiding question

What does a valid signature tell us about the received message?

1. A relationship that can be verified

An application may need to check whether a message was signed with a key it recognizes. This verification should work for both newly received messages and stored records, without requiring access to the signer’s secret.

A digital signature is a sequence of bytes calculated over a message using the private key. To verify it, the program brings together the message bytes, the signature and the chosen public key. The result tells us whether this combination is valid under the cryptographic scheme.

A scanned handwritten signature is an image that can be copied to another document. A cryptographic signature depends on the signed bytes, not on visual appearance. In a secure scheme, changing the message and recalculating its hash is not enough to produce a valid signature with the sender’s key.

2. Signing and verifying a message

We will use Ed25519 through the cryptography library. The example generates a key pair, signs a message and verifies two versions of it. The message falha de comunicação means “communication failure”; it remains in Portuguese so that the signed bytes are unchanged.

from cryptography.hazmat.primitives.asymmetric import ed25519
from cryptography.exceptions import InvalidSignature

private_key = ed25519.Ed25519PrivateKey.generate()
public_key = private_key.public_key()

original_message = "falha de comunicação"
signature = private_key.sign(original_message.encode("utf-8"))

for received_message in [original_message, "Falha de comunicação"]:
    try:
        public_key.verify(signature, received_message.encode("utf-8"))
        print("Signature verifies:", received_message)
    except InvalidSignature:
        print("Signature does not verify:", received_message)

sign() produces the signature as bytes. The for loop repeats verification for both messages, keeping the same signature and public key. When the combination does not verify, the library raises InvalidSignature, which is handled by the except block.

The first message verifies; the second does not. Try another change to the second text and run it again.

3. Preserving the signed bytes

The modified text is still readable, but its bytes no longer match the signed message.

Now consider a device that signs the bytes of a JSON file containing a test result. An application imports its data and re-exports the file. Even if it preserves the fields and values, this new representation can change the bytes. The signature was produced for the previous representation.

The verifier needs to preserve the signed bytes or reconstruct them using an exact rule agreed upon before signing. Simply saying that the two files contain the same JSON does not define which bytes enter the calculation.

4. Choosing the expected public key

A verification failure alone does not identify its cause. The message may have changed, the signature may be damaged or the chosen public key may not be the matching one. The test evaluates the combination, not each input in isolation.

Suppose someone presents a message, a signature and a public key, all prepared by that person. The combination may be valid. This does not demonstrate that the key belongs to the person you expected to receive the message from.

The association with a person or device must come from a trusted reference, such as a registry or confirmation through another established channel. A name written in the message is also just a claim. And, as we saw in the previous lesson, verification does not reveal whether the private part has been copied.

5. What the calculation still does not cover

A signature can be valid for the message falha de comunicação even if the device did not experience that failure. The calculation does not observe the test. Checking what happened requires evidence from the process; knowing whether the person responsible was allowed to approve the record requires authorization rules.

The message also remains readable. Signing does not encrypt its content or prevent copies. Restricting who can read it requires confidentiality mechanisms, such as encryption and access control for decryption keys.

What we learned

  • Signing takes the message bytes and the private part. Verification takes the message, the signature and the public part.
  • Verification depends on the bytes presented and the chosen key. A failure alone does not identify which input is wrong.
  • A valid signature does not, by itself, confirm a person’s identity, the truth of the content or permission to approve it.
  • Signing does not hide the message. Restricting who can read it requires additional mechanisms.
