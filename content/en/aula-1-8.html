Objectives

By the end of this lesson, you will be able to:

  1. explain fees as a rule governing network resource use;
  2. measure the serialized transaction and calculate its minimum fee using queried parameters;
  3. use the CIP-30 interface to separate building, signing, witness merging and submission without transferring custody of the key to the dApp;
Before you begin

Remember that a transaction consumes outputs, creates new outputs, carries verifiable fields and depends on its final bytes. Remember too that the fee is part of the accounting: inputs must cover payments, change and the fee.

Guiding question

If a transaction already specifies inputs, outputs and technical spending conditions, what else must be correct for the network to accept the package's cost and validity window?

1. Fees as a resource rule

A fee is a verifiable part of the package's design, not just a price attached outside the transaction. The network needs to limit the use of space, processing and storage. If anyone could send large or expensive packages without a proportional cost, nodes would have to spend resources without compensation and the network would be easier to overwhelm.

The fee serves two technical purposes at once. First, it assigns a minimum cost to the space and processing required, making large-scale abuse more expensive. Second, it provides an objective ledger condition: the declared fee must be at least the minimum fee calculated for the transaction under the current parameters.

Under the current rules, the base component uses a linear formula over the serialized size, a × size(tx) + b. Plutus transactions add the cost of memory and CPU execution units; reference scripts used by the transaction may add their own cost. The parameters belong to the protocol and can change. You do not need to memorize them now: you need to build the final package and query the values for the network and era you are using.

2. Size and complexity

A transaction's size matters because nodes must receive, propagate, store and validate its bytes. More fields, more metadata and more witnesses make the package larger. Even when the content looks small on screen, the final representation may include structures that do not appear in the wallet's user-friendly summary.

The package below already contains a signature and an attachment containing a 32-byte hash. PyCardano restores the transaction from CBOR and measures its complete serialization. We then remove the signature from a copy to show how much an estimate based on the incomplete package would miss.

We use a = 44 lovelace per byte and b = 155381 lovelace, queried for Preprod through the Koios API on 17 September 2026 (protocol version 11.0). These are reference values from that query, not parameters to hard-code in an application. The example uses neither Plutus execution nor reference scripts.

3. Time validity

An application usually declares a validity window to limit when its intent can be accepted. In the Cardano ledger, the lower and upper bounds are optional fields depending on the era; their absence or presence must follow the current rules and the application's policy. A finite upper bound prevents that specific proposal from remaining acceptable indefinitely.

Imagine a wallet assembling a transaction now. It selects inputs, calculates the fee, creates change and requests a signature. If that package sits idle for too long, several things can change: an input may be consumed by another transaction, network parameters may change, the user may change their mind or the application may no longer want to record that operation.

A mathematically valid signature does not make a transaction valid forever. If the signed body includes a validity interval, the ledger can only accept the package within that interval.

On Cardano, the body can declare an interval with an inclusive lower bound (invalid_before) and an exclusive upper bound (invalid_hereafter). For a slot s, the condition is invalid_before <= s < invalid_hereafter when both bounds exist. The ledger compares this interval with the slot in which the transaction is processed. The “current slot” shown by a wallet, API or explorer is not a magic transaction field: it is an external observation used by the builder to choose margins and by the operator to decide whether there is still time to submit.

4. From builder to wallet through CIP-30

An application that already knows the inputs, outputs and parameters can build the body without holding the private key. The builder selects inputs that are still available, calculates the fee for the expected final size, creates change and sets the validity interval. The signer reviews the transaction and produces witnesses over the body hash. CIP-30 standardizes this exchange between a dApp and an external wallet in the browser.

The user authorizes the connection through enable(). The dApp calls getNetworkId(), getUtxos() and getChangeAddress(). Network ID 0 identifies a test environment but does not distinguish Preprod from Preview: the wallet and the builder's provider must still point to the same testnet. UTxOs are returned as hex-encoded CBOR; the change address also comes as a hex-encoded binary representation, not necessarily the Bech32 text displayed on screen.

partialSign=true allows the wallet to sign only the part it can. With false, it must return an error if it cannot sign the entire transaction. A partial result does not demonstrate that all conditions have been satisfied. The application must gather the other signers and preserve existing scripts, datums and redeemers. Replacing the entire witness set with the last wallet's response loses components already collected.

The fee must account for all expected witnesses. If the completed transaction requires a different fee, the change affects the body and the change output: it must be rebuilt, reviewed and signed again. Auxiliary data sits outside the body, committed to by the hash inside it; is_valid also sits outside and is not directly signed by the vkey witness. Checking the body hash therefore does not remove the need to preserve the complete reviewed package.

5. Merge without losing the first signature

First, see what signing produces. The digest below is the body hash of the publication measured in section 2. A disposable key signs those 32 bytes; VerificationKeyWitness holds the public key and the signature. Verification uses the public key, the same message and the received signature.

from pycardano import PaymentSigningKey, VerificationKeyWitness, TransactionWitnessSet
from nacl.signing import VerifyKey

message = bytes.fromhex("1a2232772e3aeca8ec28f1f2bc82d36761ef1ca7084b9e010786245157a6e0f1")
key = PaymentSigningKey.generate()
witness = VerificationKeyWitness(key.to_verification_key(), key.sign(message))
VerifyKey(witness.vkey.payload).verify(message, witness.signature)
package = TransactionWitnessSet(vkey_witnesses=[witness])
print("public key:", len(witness.vkey.payload), "bytes")
print("signature:", len(witness.signature), "bytes")
print("witness set CBOR:", package.to_cbor_hex())

Change only the message passed to verify to bytes(32). Verification should fail: the signature is still 64 bytes long, but belongs to a different body. Restore the message. The keys generated here are disposable and do not control funds.

A CIP-30 response contains the witness set in CBOR. TransactionWitnessSet.from_cbor() restores its components. In the next exercise, both sets already have signatures compatible with the same body. This example combines vkey witnesses and native scripts; other components need their own handling.

Activity: preserve the package already assembled

The first set contains a signature and a script. The second adds another signature. The function already copies the package and combines scripts without duplicates, but omits the first signature. Fix the None argument in the call to combine and use Validate solution. The result should have two signatures and one script.

from copy import deepcopy
from pycardano import TransactionWitnessSet, NonEmptyOrderedSet

def combine(a, b):
    return NonEmptyOrderedSet([*(a or []), *(b or [])]) or None

def merge(existing, received):
    result = deepcopy(existing)
    result.vkey_witnesses = combine(None, received.vkey_witnesses)
    result.native_scripts = combine(existing.native_scripts, received.native_scripts)
    return result

existing = TransactionWitnessSet.from_cbor(
    "a200818258207ba06f84ca4c85d83b1ab9e73fb37dd5a005658c2515b026a0cf"
    "26f5130ad42a5840907414df5ba4ef1d1a362e2eabd3dd40081a24d9b4b6bb8b"
    "5e78e76c98345eed277f427ba99fc70d5980ae4604d1175f3b4ced3a16f7ccc2"
    "7b2a69d77e21260601818200581c70e402284201ec81d7aa495d17e52209c8bb"
    "47489395b16bcd7a2a67"
)
received = TransactionWitnessSet.from_cbor(
    "a100818258209be9aca30d6e4c708ec6c0642454e623edbeabf6975013520337"

Replace None with existing.vkey_witnesses. The function now combines both collections, and NonEmptyOrderedSet prevents duplicate components. The copy preserves the scripts and leaves the input packages unchanged. Merging does not modify the body or replace the signature verification shown before the activity.

If signing is refused or the window expires, the application stops the submission. A response from submitTx indicates submission, not inclusion. If a timeout occurs, query the ID before creating another operation: no response does not mean the transaction is absent from the network.

With CIP-30, the key stays in the external wallet, and the dApp depends on the signer's availability and approval. An application that embeds a wallet through an SDK takes on local custody; a server-side signer takes responsibility for protecting the secret and enforcing the service's authorization controls. Automation does not require handing the seed to the frontend. An ordinary dApp should never request a recovery phrase, and connecting a wallet does not silently authorize all future spending.

What we learned

  • Fees, size and resource use are part of building a transaction.
  • The measurement must include witnesses and auxiliary data. The queried parameters determine the minimum; scripts may add specific cost components.
  • The validity interval limits when a transaction can be accepted. A correctly built transaction may become unusable as time passes.
  • CIP-30 returns witnesses, which must be merged into the same transaction. Submission does not prove block inclusion.
