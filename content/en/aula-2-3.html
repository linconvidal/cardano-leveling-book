Before you begin

Guiding question

Do two events per second require two transactions per second?

1. The window turns events into publications

A service receives two events per second for one hour: 7,200 events. Its requirement is to let each event be verified against a public commitment. That does not require one transaction per event. The service can close batches and publish one Merkle root per batch.

With a fixed 60-second window, events received in the interval [0, 60) belong to the first batch; an event at time 60 belongs to the next. With a continuous stream, one hour produces 60 batches of 120 events. The application publishes 60 roots, but still needs to store and process the 7,200 events.

A larger window reduces publications but increases waiting time. With roughly uniform arrivals, the average wait for closing is close to half a window. This is not a promise about total latency: queuing, construction, submission, inclusion and the confirmation policy also factor into the measurement.

2. Do the calculations without treating the example as a budget

In Lesson 1.8, the package with a 32-byte root and one signature measured 306 bytes. With the Preprod parameters queried on 17/09/2026, a = 44 and b = 155381, its minimum fee was 168845 lovelace. We will reuse this measurement to compare publication frequencies, without rebuilding the package here.

from math import ceil

seconds = 3600
events_per_second = 2
bytes_per_event = 200
bytes_per_transaction = 306  # Package measured in Lesson 1.8.
a, b = 44, 155_381  # Preprod query used in that measurement.
fee = a * bytes_per_transaction + b
events = seconds * events_per_second

print("events:", events)
print("event bytes:", events * bytes_per_event)
print("one tx per event, ADA:", events * fee / 1_000_000)
for window in (60, 300, 900):
    publications = ceil(seconds / window)
    total = publications * fee
    print("window:", window, "publications:", publications,
          "fees in ADA:", total / 1_000_000,
          "approximate average wait:", window / 2)

The 60-, 300- and 900-second windows produce 60, 12 and 4 publications: 10.1307, 2.02614 and 0.67538 ADA under these assumptions. One transaction per event would cost 1215.684 ADA. We kept the package size the same to isolate frequency. Different inputs, signatures, attachments or parameters require a new measurement. If the application requires closing within two minutes, the 300-second window already fails that requirement, even though it costs less.

For a real budget, fix the network, era and a snapshot of the protocol parameters. Build the complete transaction, including witnesses and auxiliary data, serialize it to CBOR and calculate the fee with a compatible tool. Script transactions may include execution costs and other applicable components. An output's minimum ADA is value held in it, not the same as a fee paid.

The 7200 records of 200 bytes total 1440000 bytes. Batching reduces the number of transactions, but the application still needs to store the complete records.

An application can also carry several roots in the same transaction. This reduces submissions, but increases attachment bytes and may require waiting for other batches. It is a different design that needs a new measurement.

Activity: one publication for each minute with records

Six records arrive at seconds 0, 1, 59, 60, 61 and 180. We will group those that arrive in the same minute:

  • From 0 to 59 seconds: three records.
  • From 60 to 119 seconds: two records.
  • From 120 to 179 seconds: no records.
  • From 180 to 239 seconds: one record.

We publish one transaction for each group containing records. That means three publications. The code below still counts duplicates and returns six. Fix the count to consider each group only once.

def count_batches(times, window):
    groups = [second // window for second in times]
    return len(groups)

times = [0, 1, 59, 60, 61, 180]
print("Group for each record:", [second // 60 for second in times])
publications = count_batches(times, 60)
print("Publications:", publications)

second // 60 identifies the minute. The printed list is [0, 0, 0, 1, 1, 3]: only three distinct groups appear, 0, 1 and 3. Use Validate solution after fixing the function.

Check answer

Replace len(groups) with len(set(groups)). The set removes duplicates: {0, 1, 3} has three elements. The minute with no records does not generate a publication.

3. When the problem is frequent interaction

Publishing roots on layer 1, or L1, addresses periodic commitments to batches. A different problem arises when a defined set of participants needs to make many transfers among themselves with low latency. A Hydra Head is a multi-party state channel: UTxOs are committed on L1, transactions update the state off-chain and a protocol allows the final state to be settled on L1.

Consider three participants, A, B and C. The figure tracks 20 illustrative units, omitting L1 fees. It is not a real transaction or a performance guarantee.

Initialization defines the group and the Head's parameters. Each participant commits their selected UTxOs, not their entire wallet. Collecting the commits opens the Head. If initialization does not finish, the protocol provides for aborting and recovering the committed value.

In an open Head, nodes validate transactions using rules compatible with the eUTxO model. Numbered snapshots confirm the state through participants' signatures. A submitted transaction does not, by itself, amount to a confirmed snapshot. An unavailable participant can prevent new snapshots from being confirmed; keeping nodes responsive is part of operating the Head.

A participant can initiate close on L1 with a state permitted by the protocol. During the contestation period, another participant presents a more recent confirmed snapshot. After the applicable deadline, fanout materializes the resolved state's UTxOs on L1. Saving snapshots and monitoring L1 lets participants respond to a stale close.

Hydra is neither a private document database nor a generic rollup for any workload. Participants share Head information; movements in and out pass through L1. If one root per minute already meets asynchronous verification needs, opening a Head may merely add operational work. Compare the complete lifecycle, including commits, closing, participant availability and recovery, with the actual need for interaction.

What we learned

  • A window groups events into publications and adds waiting time before inclusion.
  • Fees depend on the transaction and parameters; proofs and files still require storage and delivery.
  • Hydra supports frequent interaction between defined participants, with snapshots confirmed off L1.
  • Closing, timely contestation and fanout resolve the state on L1.
