Objectives

By the end of this lesson, you will be able to:

  1. distinguish human intent from a technical transaction package;
  2. identify the body, witnesses, CBOR representation and bytes used in a transaction's identifier;
  3. explain how validation rules accept or reject a package;
Before you begin

You need to remember that bytes can represent text, numbers and structures; that hashes depend on the exact bytes; that digital signatures bind specific bytes to a key; and that wallet, address and network form part of the operational context.

Guiding question

How does a network go from a sentence such as "I want to record this commitment" to a package of bytes that shared rules can accept or reject?

1. Human intent and a technical package

“Send 5 units and record a document's hash” does not yet specify a transaction. The builder needs to define the network, asset, integer quantity, address, digest, authorization conditions and validity. These fields allow the operation to be verified without relying on the sentence that motivated it.

For readability, this lesson uses illustrative JSON. Real Cardano transactions use CBOR. Section 4 examines this representation and separates the logical structure, binary bytes, transport hexadecimal and JSON view.

2. Fields, rules and validation

A field is a named or defined position within a structure. It has a value and usually an expected type. A quantity field should behave as an integer. A network field should indicate a recognized context. A digest field should have a format and size compatible with the declared algorithm.

Rules are conditions the package must satisfy. Some rules check form: required field present, correct type, correct size, correct encoding. Other rules check state: resource available, credential or script condition satisfied, time validity, sufficient fee and no conflict with something already consumed.

3. Signatures within a transaction at a conceptual level

A digital signature has a role in the package: it allows the relationship between specific bytes, a signature and a public key to be verified according to a cryptographic scheme. The private key does not go inside the transaction. The package carries the signature and the information needed to check the expected key or credential.

At a conceptual level, first think of two central components. The transaction body contains the fields that describe what the operation is trying to do. The witness set contains signatures, scripts and other data used to satisfy technical conditions defined by ledger rules. The complete serialization also includes the script validity indicator and, when present, auxiliary data. These elements are not part of the transaction body or the witness set.

Consuming an output controlled by a key credential requires the corresponding key witness. Without that valid witness, the transaction fails; attached public content does not need its own document signature.

4. CBOR: from structure to Cardano bytes

The fields you have seen so far are still a logical structure. To transmit, sign and validate a transaction, Cardano needs a defined binary representation. This representation uses CBOR, short for Concise Binary Object Representation.

RFC 8949 defines how values such as integers, bytes, text, lists and maps can be encoded. CBOR does not define the meaning of a Cardano transaction. The ledger rules and era specification define which fields exist, their types and the accepted combinations.

A small CBOR map

Consider the teaching example {"rede": "preprod", "quantidade": 5}, where the fixed keys mean “network” and “quantity”. A deterministic encoding of this map produces 26 bytes. Written in hexadecimal, they look like this:

a2                                      # map with 2 pairs
  64 72656465                           # text "rede"
  67 70726570726f64                     # text "preprod"
  6a 7175616e746964616465               # text "quantidade"
  05                                    # integer 5

continuous hex:
a264726564656770726570726f646a7175616e74696461646505

Real transactions contain larger structures and era-specific fields. Addresses, hashes and identifiers appear as bytes, not as the human-readable text displayed by the interface. Do not try to build this CBOR manually: use an era-compatible library and check the structure before signing.

From a Python object to CBOR

With PyCardano, fields are held in a TransactionBody object. This example has one input, one output of 100 ADA, a fee of 200000 lovelace and a validity limit at slot 1000. The input is fictitious: we are studying the body, not preparing a transfer for submission.

inputs identifies the resource being consumed; outputs describes the destination and value. fee holds the fee and ttl holds the upper validity bound. Run the code to see these fields serialized by to_cbor_hex().

from pycardano import (
    Address, TransactionBody, TransactionId, TransactionInput,
    TransactionOutput, Value,
)

destination = Address.from_primitive(
    "addr_test1qz5p9x623ngvjtzf89gcz2pjhxcahq7rper4q534ejegyd406v8dc860wkryxpgsaeqzvwz7y2nmp7caz35yfpqsw7as9v22t0"
)
body = TransactionBody(
    inputs=[TransactionInput(TransactionId(bytes(32)), 0)],
    outputs=[TransactionOutput(destination, Value(100_000_000))],
    fee=200_000,
    ttl=1000,
)
print(body.to_cbor_hex())

The output is the CBOR body written in hexadecimal. TransactionBody.from_cbor() performs the reverse operation: it takes this representation and recovers the object's fields.

Body, identifier and witnesses

The transaction body is serialized before witnesses are collected. In Cardano, the transaction identifier is the Blake2b-256 digest of the transaction body's CBOR bytes according to the ledger era. Vkey witnesses sign this same body hash. The signature cannot be part of the bytes over which it is calculated; it goes into the transaction witness set attached to the body. The witness set can also carry scripts, datums and redeemers required by the transaction, depending on the era and script type.

This scope must be explicit. The transaction ID and vkey witness do not directly cover the witness set or the is_valid indicator, which sits outside the body in the complete serialization. Auxiliary data also sit outside, but their bytes are indirectly committed to by the auxiliary_data_hash included in the body. The ledger validates the complete combination under the era's rules; a valid key witness does not mean that every byte outside the body was signed by that key.

The transaction ID is an opaque digest, without a textual prefix identifying the network. The body may include the optional network_id field, and output addresses or reward accounts carry network context in their encodings. Even so, the wallet, node, API and parameters must be configured for the same environment. Record the network separately and do not use the transaction ID alone to distinguish Mainnet, Preprod or Preview.

In interfaces such as CIP-30, CBOR bytes commonly cross the API written in hexadecimal. An argument named cbor or a string such as 84a4... is not JSON, contract text or secret material. It is a textual representation of the serialized bytes.

Valid CBOR is not enough

CBOR allows more than one valid way to represent certain values. Cardano restricts the structure with its own rules and era-specific CDDL descriptions. A library must produce the form accepted by the ledger, not just any document a CBOR decoder can read.

5. Ed25519 and the message of a key witness

In Lesson 0.4, we used Ed25519 to sign the bytes of a message. Ed25519 is a real EdDSA signature scheme over the Edwards25519 curve, specified in RFC 8032. Curve, scheme, implementation and protocol usage are distinct layers: Cardano determines which message must be passed to the library.

In the Ed25519 format, the public key is 32 bytes and the signature is 64 bytes. Signing takes private material and a message as bytes; verification takes the public key, the same message and the signature. Ed25519 uses SHA-512 internally and derives its ephemeral value deterministically; the application does not invent a nonce for the operation. Private key formats vary between a seed, an expanded key and an opaque object. Extended keys from a Cardano wallet are not interchangeable with just any file labeled “Ed25519”.

For a Cardano vkey witness, the message is the 32-byte body hash, calculated with Blake2b-256. Signing this digest according to the protocol does not mean using the Ed25519ph variant. Nor does it mean signing its 64 hexadecimal characters: hex text and decoded bytes are different inputs. The witness contains a verification key and a signature. For key-controlled spending, the ledger verifies the signature and relates the verification key's hash to the required credential. There are also required signers and script conditions; verifying an isolated signature does not verify the entire transaction.

From the body to the message to be signed

Now recover the serialized body from the previous example and call hash(). Compare the 32-byte digest with the 64 characters in its hexadecimal representation. Signing takes the digest bytes.

from pycardano import TransactionBody

body = TransactionBody.from_cbor(
    "a400818258200000000000000000000000000000000000000000000000000000"
    "00000000000000018182583900a8129b4a8cd0c92c493951812832b9b1db83c3"
    "0e47505235ccb28236afd30edc1f4f7586430510ee4026385e22a7b0fb1d1468"
    "44841077bb1a05f5e100021a00030d40031903e8"
)
digest = body.hash()
print("digest:", len(digest), "bytes")
print("hex:", digest.hex())
print("hex as text:", len(digest.hex().encode("ascii")), "bytes")
print("same input?", digest == digest.hex().encode("ascii"))
Activity: correct the fee, preserve the validity limit

The fee needs to change from 200000 to 200001 lovelace, keeping the validity limit at 1000. The function below changes the wrong field. Correct only that assignment and use Validate solution.

The body from the previous example is already in CBOR. The function must return the revised body and its corresponding hash: changing the fee also changes the message that will be signed.

from pycardano import TransactionBody

example_body = TransactionBody.from_cbor(
    "a400818258200000000000000000000000000000000000000000000000000000"
    "00000000000000018182583900a8129b4a8cd0c92c493951812832b9b1db83c3"
    "0e47505235ccb28236afd30edc1f4f7586430510ee4026385e22a7b0fb1d1468"
    "44841077bb1a05f5e100021a00030d40031903e8"
)

def signer_message(body_cbor_hex, new_fee):
    body = TransactionBody.from_cbor(body_cbor_hex)
    body.ttl = new_fee
    return body.to_cbor_hex(), body.hash()

body_hex, message = signer_message(example_body.to_cbor_hex(), 200_001)
revised = TransactionBody.from_cbor(body_hex)
print("fee:", revised.fee, "validity limit:", revised.ttl)
print("message:", message.hex())
Check answer

Replace body.ttl = new_fee with body.fee = new_fee. The fee becomes 200001 lovelace and the validity limit remains 1000. The hash is calculated after the revision. If someone had already signed the previous body, that signature would not work for the body with the new fee.

A valid witness binds a key to a body. The record linking the key to a person, its period of validity and that person's authority to approve the document remain separate evidence. The signer should review the effects before signing, because a correct signature over the wrong body still authorizes the operation described by that body.

What we learned

  • A transaction is a structured package describing an operation for the network to verify.
  • Structure, CBOR representation, transaction body and witnesses have distinct roles. The identifier depends on the body bytes.
  • A vkey witness uses Ed25519 over the binary Blake2b-256 body hash, not its hexadecimal text. Acceptance still depends on the other ledger rules.
