Objectives

By the end of this lesson, you will be able to:

  1. distinguish metadata attached to a transaction from a native asset represented by the ledger;
  2. explain why the policy ID is part of an asset's identity;
  3. interpret asset names as bytes and evaluate a native script with signature and time conditions;
  4. explain how minting, burning and transfers affect integer quantities under a minting policy.
Before you begin

Remember that a transaction consumes outputs and creates new ones, that fees depend on the package's final bytes, and that metadata is a structured attachment, not automatic proof of external truth.

Guiding question

If two assets appear with the same name in an interface, when does the network treat them as the same asset and when does it treat them as different assets?

1. The concept of a native asset

A native asset is an asset that the ledger can represent directly in an output's value. Instead of appearing only as text in metadata, it appears as a quantity in the transaction's accounting.

Imagine an output with a value like this:

Value component Quantity
ada 10
asset defined by a policy and a name 50

Writing name: TOKEN in metadata does not create units in the ledger. A native asset appears in output values, but does not inherit ADA's role in fees, staking, deposits or governance.

2. Policy ID as part of identity

The policy ID is part of the asset's identity. On Cardano, it is the 28-byte hash of the minting policy, usually displayed as 56 hexadecimal characters. It is not a freely chosen label. The policy defines the technical conditions that allow positive or negative minting of that asset; institutional authority and purpose remain external.

The example uses two policy IDs calculated from signature policies. ScriptHash holds the ID; AssetName holds the name bytes. MultiAsset organizes quantities first by policy and then by name.

from pycardano import ScriptHash, AssetName, Asset, MultiAsset

p1 = ScriptHash(bytes.fromhex("b42438993a121732d88cf0719ef8a895953e5cd686c48782bccec209"))
p2 = ScriptHash(bytes.fromhex("d3b22f481e20b76f395e04df54fc7e480c385cdc83f9b99412d295dd"))
name = AssetName(b"TOKEN")
lowercase = AssetName(b"token")
balance = MultiAsset({p1: Asset({name: 50, lowercase: 3}), p2: Asset({name: 7})})
for policy, assets in balance.items():
    for asset_name, quantity in assets.items():
        print(policy.payload.hex(), asset_name.payload.hex(), quantity)
print("CBOR:", balance.to_cbor_hex())

The output shows three distinct identities. There are 50 units of TOKEN and 3 of token under b42438993a12…, and 7 of TOKEN under d3b22f481e20…. Creating this Python object describes a value; issuing the units in the ledger requires a minting transaction authorized by the policy.

Using only TOKEN as a database key can mix up balances of assets with different policies.

3. Asset names as bytes

An asset name is not, conceptually, a word. It is a sequence of zero to 32 bytes. Those bytes are often chosen to form readable UTF-8 text, but that is a choice made during issuance and integration, not a universal guarantee.

This is why tools often display asset names in hexadecimal. Hexadecimal is a stable way to write bytes. Each pair of hex characters represents one byte. For example, the text TOKEN, encoded as UTF-8, becomes the bytes:

54 4f 4b 45 4e

544f4b454e

An empty asset name is also possible. In that case, the identity still needs to be read carefully: the asset name is a zero-length byte sequence, not text accidentally left out.

4. Integer quantities, minting, burning and transfers

The ledger accounts for each native asset in integer quantities. If an interface displays decimal places, that scale belongs to the application's schema and presentation; the on-chain value remains an integer. The smallest unit must therefore be defined before issuing or integrating the asset.

For a specific asset_id, conservation can be expressed compactly as:

quantity in inputs + quantity in mint = quantity in outputs

The mint field uses signed quantities. A positive value creates units; a negative value removes units that also enter through the inputs; zero means the transaction does not change that asset's total quantity. Both positive and negative minting require the corresponding minting policy to be executed and satisfied.

OperationAsset inputsMintAsset outputsInterpretation
Mint0+100100The total quantity increases by 100.
Transfer70020 + 50The same 70 units are redistributed among outputs.
Burn100-2575Twenty-five units are removed from the accounting.

Transferring is not minting again. When mint = 0 for the asset, its minting policy is not executed merely because of the transfer; the inputs' spending conditions are still checked. Minting and burning, however, use the mint field and must satisfy the policy whose hash forms the policy_id.

Activity 1: check asset conservation

Assume each line describes all the inputs, the mint field and all the outputs for the same asset_id. Classify each line as mint, transfer, burn or invalid, and justify your answer using inputs + mint = outputs.

  • A: inputs 0; mint +60; outputs 60.
  • B: inputs 60; mint 0; outputs 15 + 45.
  • C: inputs 60; mint -10; outputs 50.
  • D: inputs 60; mint 0; outputs 55.
Check answer

A is mint: 0 + 60 = 60. B is a transfer: 60 + 0 = 15 + 45, with no change in the total quantity. C is burn: 60 - 10 = 50. D is invalid in this example, which lists all inputs and outputs, because 60 + 0 does not equal 55. In A and C, the minting policy must be executed and satisfied; in B, it is not executed again merely because of the transfer.

5. Native scripts: which keys, in which interval?

A minting policy can be a native script, combining signature and time conditions. The same type of script can also serve as an output's spending credential. The control points are distinct: the policy checks minting or burning under its policy ID; the spending credential checks consumption of the eUTxO. Owning a token does not automatically grant the ability to issue more units.

The native format provides sig to require a key, all and any to combine conditions, and atLeast to require a threshold. Timelocks use after and before. The rule compares the transaction's validity bounds: after 100 requires a lower bound of at least 100; before 200 requires an upper bound of at most 200. The ledger also checks that the processing slot falls within the interval. A signature created before the deadline does not authorize inclusion after it.

In PyCardano, ScriptNofK(2, ...) requires two of the signature conditions. ScriptAll combines that threshold with both time conditions. The credentials below are hashes of three public keys used for study.

from pycardano import (
    VerificationKeyHash, ScriptPubkey, ScriptNofK, ScriptAll,
    InvalidBefore, InvalidHereAfter,
)

keys = [
    VerificationKeyHash(bytes.fromhex("70e402284201ec81d7aa495d17e52209c8bb47489395b16bcd7a2a67")),
    VerificationKeyHash(bytes.fromhex("b44173e4bc81916bb53443b01ce8d8d635b618ca7fa197265a0cb2a2")),
    VerificationKeyHash(bytes.fromhex("d5c6555b5a7c12cc53893955e9b779c9320afb2411994a5c70cee206")),
]
signatures = ScriptNofK(2, [ScriptPubkey(key) for key in keys])
policy = ScriptAll([InvalidBefore(100), InvalidHereAfter(200), signatures])
print("CBOR:", policy.to_cbor_hex())
print("policy ID:", policy.hash().payload.hex())

Run the code, then change the bound from 200 to 201. The policy has changed, so its CBOR and policy ID change too. Restore 200. To satisfy the original policy, a transaction can use the interval [120, 180) and valid signatures from two of those keys. Serializing the script does not run ledger validation.

The native script does not read the datum, redeemer or metadata, and does not inspect the asset name or minted quantity. Thus, “two signatures before the deadline” does not by itself enforce a maximum supply of 100 or one-time issuance.

Activity 2: do not count the same key twice

The function should build the same policy requiring two of three distinct keys, within the supplied window. But one credential appears twice. Fix the repeated reference without changing the threshold or the bounds, and use Validate solution.

from pycardano import (
    VerificationKeyHash, ScriptPubkey, ScriptNofK, ScriptAll,
    InvalidBefore, InvalidHereAfter,
)

def create_policy(keys, start, end):
    signatures = ScriptNofK(2, [
        ScriptPubkey(keys[0]), ScriptPubkey(keys[0]), ScriptPubkey(keys[2])
    ])
    return ScriptAll([InvalidBefore(start), InvalidHereAfter(end), signatures])

keys = [
    VerificationKeyHash(bytes.fromhex("70e402284201ec81d7aa495d17e52209c8bb47489395b16bcd7a2a67")),
    VerificationKeyHash(bytes.fromhex("b44173e4bc81916bb53443b01ce8d8d635b618ca7fa197265a0cb2a2")),
    VerificationKeyHash(bytes.fromhex("d5c6555b5a7c12cc53893955e9b779c9320afb2411994a5c70cee206")),
]
policy = create_policy(keys, 100, 200)
print("CBOR:", policy.to_cbor_hex())
print("policy ID:", policy.hash().payload.hex())
Check answer

Replace the second occurrence of keys[0] with keys[1]. With A, A and C, the same signature from A can satisfy both repeated conditions. With A, B and C, the threshold requires two distinct credentials. PyCardano serializes both versions: producing CBOR does not guarantee that you wrote the intended policy. The tests check the constructed structure without simulating a transaction's acceptance by the ledger.

Even a valid combination of two keys does not prove the involvement of two independent people or a valid decision-making process. The external process must link keys to responsible parties and roles. Also, if the policy stops accepting minting after a deadline, the same time restriction may prevent burning; removal from circulation must be planned before issuance.

6. A short EAC accounting example

An environmental attribute certificate (EAC) has a unit and criteria defined by an external methodology. In this example, an external decision authorizes 8,400 whole units of the asset with UTF-8 name EAC-DEMO-VINTAGE-A. Under the same policy ID and with no other issuance, minting +8400 followed by retirements through burning -1250 and -700 leaves 6,450 units.

supply = 0
for mint in (8400, -1250, -700):
    supply += mint
    print("mint:", mint, "supply:", supply)

The output is 8400, 7150 and 6450. To perform each burn, the transaction must bring in the units being removed through its inputs and satisfy the policy. A transfer does not change supply. Adding three operations demonstrates the global supply only if the minting and burning history is complete. The ledger does not measure the environmental benefit or prevent double counting in another system. This example uses burning for retirement; the institutional meaning of that operation is defined outside the protocol.

7. CIP-25 for describing media tokens

CIP-25 is a metadata convention for media tokens under label 721, associating policy ID and asset name with fields such as name and image. It is not a universal standard for every native asset and is not needed for EAC arithmetic. A name and image displayed by a wallet do not replace the technical identity.

This metadata remains in the positive-minting transaction. Transferring the asset neither moves nor edits it. Under the standard, a later publication treated as an update also depends on positive minting under the corresponding policy; burning does not satisfy that rule. A policy that has already closed may prevent such an update. When an application needs replaceable reference state, CIP-68 offers a different design, which we will study after Plutus.

What we learned

  • A native asset appears in the value accounted for by the ledger. Descriptive metadata alone does not create that asset.
  • Technical identity combines policy ID and asset name. A visible name or label is not enough to identify the asset.
  • Asset names are bytes; text and hexadecimal are ways to represent them.
  • Minting and burning change supply under the policy; transfers only redistribute units. EAC arithmetic does not prove the external benefit.
  • Native scripts combine keys and time in minting or spending roles. CIP-25 describes media tokens without enforcing rules on their content.
