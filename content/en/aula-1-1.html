Objectives
  1. Distinguish applications, access services and network nodes.
  2. Distinguish a query, transaction submission and inclusion in the history.
  3. Explain why changing an interface does not change the network rules or erase published records.
Before you begin

The concepts of hashes and signatures from Module 0 will help you follow this lesson. You do not need to know about blockchain or install a wallet.

Guiding question

What does an application do on its own, and which operations require the Cardano network?

1. The application and the infrastructure it uses

A web application usually has an interface, services that receive requests and somewhere to store data. When someone submits a form, for example, the application checks the data it receives and decides what to record. The developers can change its rules, reorganize storage or replace the interface as the product evolves.

When this application uses Cardano, it connects to an existing network that other applications also use. Some requests retrieve information already recorded; others propose new operations. Querying these data and requesting the inclusion of an operation are two different uses of the network.

Cardano is a public network of computers connected over the internet and operated by different people and organizations. These computers are called nodes. They exchange information about operations and check what they receive before accepting a change to the record they maintain. The shared set of rules governing this communication and these checks is the protocol.

A public network

Application developers can query Cardano's public data and build services that use them. They can also operate a node, taking on the work of keeping that software connected and up to date. Participating in the network does not require belonging to the organization that created a particular application.

Node operators can be different people or organizations. This matters because distributing servers across several locations is not enough to distribute control: a company could maintain all of them and decide on its own which operations to accept.

On Cardano, each node checks the operations it receives. If an operator modifies their node's software to accept an operation without a required signature, the other nodes following the protocol will reject it because that signature is missing.

Node implementations

The program an operator installs is a node implementation. cardano-node is the reference implementation in Haskell, originally developed by Input Output Global (IOG). Other projects are developing their own implementations in different languages:

  • Amaru, in Rust, by PRAGMA.
  • Dingo, in Go, by Blink Labs.

These programs may organize their code differently, but to participate in the same Cardano network, they must communicate compatibly and apply the same verification rules. The signature required in the previous example must be checked regardless of the language the node is written in.

The projects are at different stages and have different limitations. Before using a release to operate a node, check its repository for supported features and networks and whether the maintainers recommend it for production use. To discover other projects, see the Cardano node catalog on the Cardano Developer Portal.

2. How the application queries the network

The application can query Cardano data through an API, an interface for communication between programs. It sends a request to a service connected to the network and receives a response with the requested information.

From the record to the query response

The node tracks the network's records, but an application may need to search this information in various ways. To support queries by period or identifier, for example, a service can use an indexer: software that reads the node's data and organizes them in a database for querying. The API can retrieve the answer from this database without scanning the entire history for each request. You can find examples in the indexer catalog.

Services such as Blockfrost and Koios offer APIs for querying Cardano data. Application developers can use these services or operate a node with their own query services. In the latter case, they also need to keep the data up to date and access available. Other access options are listed in the API provider catalog.

A provider may require registration, limit queries or charge for access. These conditions belong to the service it offers. Switching providers may require new credentials, different API calls and adjustments to response formats, even though the application is still querying the same network.

If the API stops responding, the application may be left without the data it needs to display. The error indicates a failure along that query path; by itself, it does not tell you whether nodes are still accepting operations. A response may also contain outdated data if the service has not yet caught up with the latest records.

3. How an operation enters the record

Querying published data does not add an operation to the history. To propose a change, the application must prepare a transaction. It describes the intended operation and gathers the required authorizations in a format the nodes can verify.

A transfer of ADA, Cardano's currency, is one example: the transaction specifies which funds will be used and where they will go. Nodes check authorizations, such as the signatures studied in Module 0, and verify that the funds are still available. A transaction can also publish data or create other digital assets, provided it meets the applicable rules.

Submitting and tracking the result

The prepared transaction must reach a node. The application can send it through a submission service, which receives the data and forwards them to the network. This service may be available through the same API used for queries. A message saying the service received the submission confirms that step; the result still needs to be tracked to determine whether the operation entered the history.

The checks performed by nodes can prevent a transaction from being accepted. If a required signature is missing, for example, resubmitting the same data through another provider does not supply it. Credentials used to access the API authorize use of the service; they do not replace the authorizations required in the transaction. The operation must also cover network fees, which are separate from any provider charges.

The history and the current state

Nodes that produce blocks gather transactions and propose their inclusion in the history. The other nodes verify the blocks they receive. Each block contains a hash reference to the previous one; these links form the blockchain, or chain of blocks. The choice of which chain to follow is governed by the protocol's consensus rules.

Verifying a new transaction depends on the results of previous ones. The ledger encompasses the network's current state, such as the resources available to spend, and the rules used to update it. Each node applies these rules to the transactions in the blocks it accepts. This state can be reconstructed from the blockchain's history.

After submission, the application can query a source that reports the transaction's inclusion in a block. This observation differs from the submission service's initial response. Depending on the use case and risk, the application may wait for more blocks before treating the operation as complete. This is an example of a confirmation policy, discussed in Lesson 1.3.

4. What remains in the application

Interface rules and network rules

Disabling a submit button can prevent a mistake in the interface, but someone can still try to build the transaction using another program. When the protocol requires an authorization, nodes check it regardless of the interface used. Application developers therefore need to know which restrictions exist only in their software and which will also be checked by the network.

Other applications can query the same records

A wallet queries assets and manages the use of keys to authorize transfers. A reporting system can use the same records to present a history of operations. Each application organizes information for its own purpose; the application that created a transaction need not be the only one able to query it.

Choosing what to publish

The application may need to store users' personal data and documents that must not become public. These data require their own storage and access controls. Using Cardano does not require publishing the system's entire contents; you need to choose which information can be part of a public transaction.

Once published, information can be copied and queried outside the application. Removing it from a screen changes its presentation but does not erase the publication from the blockchain. This must be considered before submission, while it is still possible to decide what to disclose.

The interface, documents and private services also still need hosting and maintenance. The application operator is responsible for keeping them running and for the information shown to users. The network checks the operations it receives according to the protocol, without taking on the operation of these other services.

Activity 1: follow the query and submission

An application uses a provider's API to query records and submit transactions to Cardano. In each situation below, choose the conclusion supported by the observation.

1. When querying a history, the application receives a “service unavailable” message from the API. No data are returned. What message can the application show the user?

2. When submitting a transaction, the application receives the response “received for forwarding”. This response does not identify a block. What does it confirm?

3. A node rejects a transaction because a required signature is missing. The application resubmits the same data through another provider without adding the signature. What changes?

4. A website starts hiding an already published record by changing only the page's display filter. What is the scope of this change?

0 of 4 questions answered.

Check answer
  1. The first option describes the observation: the query failed at that service. A failure to retrieve data does not show that the history is empty or that block production has stopped. Revisit the query path if you attributed the error directly to the network.
  2. The second option distinguishes receipt by the service from inclusion in the history. The absence of a block in this response does not demonstrate rejection either. The submission's result must be tracked, as described in How an operation enters the record.
  3. The third option retains the signature requirement. API credentials allow use of the access service but do not authorize spending the funds. The new provider may receive the submission; the same data still fail to meet the condition required by the nodes.
  4. The first option limits the change to the page where the filter was applied. The website did not erase the record from the network or change the service queried by other applications. The indexer follows network data, not each website's display decisions. Revisit choosing what to publish to review this distinction.

What we learned

  • The application queries data through access services, which may use indexers to organize network information. A failure along this path does not, on its own, demonstrate a failure of the entire network.
  • A transaction proposes an operation. Receipt by the submission service and inclusion in a block are separate stages that the application needs to track.
  • Nodes verify transactions and blocks according to the protocol. The blockchain's history allows the ledger state to be reconstructed.
  • The interface and private data still need their own services. A change on screen neither waives network authorizations nor erases already published records.
