Objectives
  1. Turn bytes into leaves and combine hashes up to a root.
  2. Build a minimal proof for one item among four.
  3. Fix a verifier that confuses left/right order.
Before you begin

You need to be able to calculate hashes of bytes and understand why the expected reference must come from outside the presented material. Review Lesson 2.1 for that second distinction.

Guiding question

How can we check event B without also receiving files A, C and D?

1. Four files, one commitment

A service closes a batch containing four event files, called A, B, C and D. B's recipient wants to verify that they received the bytes included in that batch. Delivering all the files would work, but would increase traffic and provide access to content they did not request.

A Merkle tree combines hashes in levels. Each file produces a leaf. Two adjacent hashes produce a parent hash, and the process continues until only the root remains, also called the root hash. A SHA-256 root has 32 bytes, even when it represents many files. This does not compress the files in a recoverable way: the root cannot reconstruct them.

The order of the batch is part of the design. A occupies index 0; B, index 1; C, index 2; D, index 3. The service preserves this order and the calculation recipe alongside the files.

2. The recipe comes before the tree

The example uses four leaves. The files are exact texts encoded in UTF-8, with no trailing newline. H means SHA-256; || means concatenating bytes, not their hexadecimal representations.

  • Leaf: H(0x00 || data).
  • Internal node: H(0x01 || left_hash || right_hash).

The prefixes 0x00 and 0x01 distinguish a leaf from an internal node. The leaf depends on the file's bytes. Its position is given by the path through the tree. Each internal node combines two 32-byte binary digests, preserving left/right order.

Sorting the digests by value or concatenating their hexadecimal text would change the recipe. Whoever builds and whoever verifies the tree must use the same rules.

3. Calculate the root and open a path

Run the code. The functions return binary digests; .hex() is used only for display. B's proof contains two pairs: the sibling's side and its hash. The path is followed from bottom to top. The fixed proof codes E and D mean left and right, from Portuguese esquerda and direita. The file texts retain criado (created), revisão (review) and correção (correction) as exact hash inputs.

import hashlib

def leaf(data):
    return hashlib.sha256(b"\x00" + data).digest()

def node(left, right):
    return hashlib.sha256(b"\x01" + left + right).digest()

files = [text.encode("utf-8") for text in [
    "T-0141|criado", "T-0142|revisão",
    "T-0143|criado", "T-0144|correção",
]]
A, B, C, D = [leaf(data) for data in files]
published_root = node(node(A, B), node(C, D))
proof_B = [("E", A), ("D", node(C, D))]

recalculated = leaf(files[1])
for side, sibling in proof_B:
    recalculated = (node(sibling, recalculated) if side == "E"
                  else node(recalculated, sibling))
print("root:", published_root.hex())
print("inclusion:", recalculated == published_root)

B_modified = leaf(files[1] + b"!")
print("modified file:", node(node(A, B_modified), node(C, D))
      == published_root)
print("hash bytes in the proof:", sum(len(h) for _, h in proof_B))

The output shows inclusion True, modified file False and 64 bytes of hashes in the proof. The package still needs to carry file B, the sides and the root's location. If the query specifies an index, the path must also match that position. “64 bytes” is not the size of a transaction or of the whole package.

Try changing the first side in the proof from ("E", A) to ("D", A), keeping the published root. The comparison fails. If you also change the expected root, you will no longer be testing the previous commitment. In the application, obtain the root from the already checked publication, not from a replaceable field in the sender's package.

4. Fix the orientation

Activity: the sibling may be on the left

This verifier places the sibling on the right at every step. It works for A, but rejects B. Fix the calculation inside the loop to respect E and D. Keep the checks for the index, number of siblings and expected side. Run it to observe the failure, then use Validate solution to test other files, positions and tampering.

The path check is already in place: at an even position, the sibling is on the right; at an odd position, on the left. Integer division by two finds the parent's position at the next level.

import hashlib

def leaf(data):
    return hashlib.sha256(b"\x00" + data).digest()

def node(left, right):
    return hashlib.sha256(b"\x01" + left + right).digest()

def verify_inclusion(index, data, proof, root):
    if not 0 <= index < 4 or len(proof) != 2:
        return False
    current = leaf(data)
    position = index
    for side, sibling in proof:
        expected_side = "E" if position % 2 else "D"
        if side != expected_side:
            return False
        current = node(current, sibling)
        position //= 2
    return current == root

files = [b"A", b"B", b"C", b"D"]
A, B, C, D = [leaf(d) for d in files]
root = node(node(A, B), node(C, D))
proof = [("E", A), ("D", node(C, D))]
print("B included:", verify_inclusion(1, b"B", proof, root))
Check answer

For E, use node(sibling, current); for D, use node(current, sibling). B first needs LA on the left and then N(C,D) on the right. D requires siblings on the left at both levels. Testing only A would therefore hide the bug.

The verifier keeps the root fixed. If a comparison fails, obtain the original file and check the recipe, index and proof before attributing the mismatch to tampering.

5. What grows and what remains outside the proof

In a complete binary tree with 1,024 leaves, each path has ten levels. Ten siblings, or 320 bytes of SHA-256 hashes, are enough, instead of the other 1,023 files. The number of siblings grows logarithmically with the number of leaves, while building the tree still requires processing the batch.

This lesson fixes four leaves to avoid hiding a format decision. For arbitrarily sized batches, the construction must define the tree's shape, how it handles levels with an odd number of nodes and how it commits to the count. Duplicating the last leaf and splitting into subtrees of different sizes are distinct conventions. An inclusion proof is also not proof that a new log preserved the whole old one. Growing logs can use specific consistency proofs; that requires a different recipe.

Inclusion confirms that those bytes, at that position, reconstruct the expected root. It does not reveal files that went uncaptured or prove that B's result is true. Nor does it automatically provide confidentiality: sibling hashes of predictable data may allow guessing attempts. We will address this exposure in Lesson 2.4.

What we learned

  • Leaves and internal nodes use different recipes, with explicit bytes and ordering.
  • B's proof contains LA and N(C,D), with their sides, without requiring the other files.
  • Changing the file, position, sibling or orientation invalidates the comparison against the same root.
  • The root commits to the batch; availability, completeness of capture and confidentiality require additional controls.
