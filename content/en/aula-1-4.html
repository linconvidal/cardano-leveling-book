Objectives
  1. Distinguish the role of a CIP from the process that brings a network change into effect.
  2. Recognize the governance participants and their role in parameter changes.
  3. Explain why transaction construction depends on the current parameters.
Before you begin

Revisit the distinction between application and protocol introduced in Lesson 1.1, and the concept of an epoch from Lesson 1.3.

Guiding question

How does a change discussed in the ecosystem come to affect the transactions an application can submit?

1. CIPs: agreeing on how tools work together

A wallet and an application developed by different teams need to agree on formats and interfaces. Cardano Improvement Proposals, or CIPs, document proposals, standards and conventions for this collaboration. They also record discussions about protocol changes.

CIP-19, for example, describes the address structure we will study in the next lesson. CIP-30 standardizes communication between an application and a browser wallet. In the latter case, wallets and applications implement the interface; this does not require each call to be decided by a network vote.

The drafting and review process is described in CIP-1. A CIP's status indicates its stage in that process. Publishing the document does not install software, guarantee that every tool implements it or automatically change the rules applied by nodes.

2. What governance decides

Choices that affect the entire network require shared decision-making mechanisms. On-chain governance records actions and votes for decisions provided for in the protocol, such as changing parameters, initiating a protocol upgrade or authorizing a treasury withdrawal.

The model described in CIP-1694 brings together three groups with distinct roles:

  • DReps are representatives to whom ADA holders can delegate voting power. They vote on actions in which this group participates.
  • Stake pool operators (SPOs) participate in decisions assigned to this group, including protocol upgrades and changes to security-relevant parameters.
  • The constitutional committee assesses actions for compliance with the Cardano Constitution in decisions where its approval is required.

The participating groups and approval thresholds depend on the action type. Delegating voting power to a DRep neither transfers ADA to them nor gives them the keys that authorize payments.

A CIP can provide the technical basis for a change. The governance action, its votes and its enactment are events distinct from the document's editorial process.

3. Parameters that affect the application

The protocol uses parameters to define limits and costs. They directly affect the work of building transactions:

  • The maximum transaction size limits how many bytes a transaction can occupy.
  • Fee coefficients contribute to the calculation of how much a transaction must pay.
  • Execution limits restrict the resources scripts can consume.

The maximum block size is also a parameter. Increasing it may allow more data per block, but places greater transmission and processing demands on nodes. This choice affects operators and applications, not just a product's screen.

Changing a parameter already provided for in the protocol differs from introducing a new rule that the software does not yet recognize. A protocol upgrade may require new node versions and a coordinated transition, such as a hard fork.

4. From approval to the value in effect

A ratified action has met the approval conditions. It takes effect when it is enacted, according to the protocol rules. Parameter updates are applied at epoch transitions; receiving favorable votes does not immediately change the limit a node uses to check a transaction.

Suppose a change increases the maximum permitted size. A transaction exceeding the current limit does not become acceptable just because the change was announced or approved. Until enactment, the previous limit continues to apply.

When building a transaction, the application obtains the target network's current parameters through a node or access service. It should not treat a value copied from a proposal as if it were already the network configuration. If preparation spans an epoch transition, the parameters must be checked again before completing or submitting the transaction. A change to the body may require new signatures.

An action increasing the maximum transaction size has been ratified but not yet enacted. The application is about to submit a transaction that exceeds the current limit but fits within the new one.

What we learned

  • CIPs document proposals and standards that help tools and participants work compatibly.
  • Governance involves DReps, stake pool operators and the constitutional committee, with participation and conditions defined by action type.
  • Network parameters affect transaction size, costs and execution limits.
  • Ratification and enactment are different stages. The application must work with the values currently in effect.
