Objectives
  1. Calculate the SHA-256 of a UTF-8 encoded message.
  2. Compare hashes and explain the effect of changing a message.
  3. Recognize the limits of this comparison, including collisions and the source of the reference.
Before you begin

To follow this lesson, you need to know how to convert text to UTF-8 bytes and recognize hexadecimal notation, as we did in Lesson 0.1.

Guiding question

What can we conclude about data by comparing hashes?

1. Content-based references

Programs may need to recognize duplicate content or detect changes to data. One way to support these tasks is to calculate a reference from the content bytes themselves, rather than relying only on names or assigned identifiers.

A hash function performs this calculation. It transforms a sequence of bytes into a fixed-size value called a hash.

We will use SHA-256, a cryptographic hash function. Its hash is 256 bits, or 32 bytes, which can be written as 64 hexadecimal characters.

To observe the calculation, use the message falha de comunicação (“communication failure”). The example changes only f to F and shows each message alongside its hash. The Portuguese text is kept unchanged because its exact bytes determine the hashes shown.

import hashlib

original_message = "falha de comunicação"
modified_message = "Falha de comunicação"

original_message_bytes = original_message.encode("utf-8")
modified_message_bytes = modified_message.encode("utf-8")
original_hash = hashlib.sha256(original_message_bytes).hexdigest()
modified_hash = hashlib.sha256(modified_message_bytes).hexdigest()

print(original_message, original_hash, sep="\t")
print(modified_message, modified_hash, sep="\t")

The hashlib.sha256 function calculates the hash of the bytes, and hexdigest() writes the result in hexadecimal. The output shows two different hashes, each with 64 characters. Try another change to modified_message and run it again.

If you repeat the calculation without changing the messages, the hashes will repeat. With the same bytes and the same algorithm, the result is always the same. This property is called determinism.

In the pair we observed, a small change to the input changed much of the hash. This behavior is called the avalanche effect.

2. What the comparison tells us

When using the same algorithm, different hashes demonstrate that the bytes are different. The hash does not identify the changed character, measure how similar the contents are or tell us whether the change was authorized. To locate a difference, we need to compare the contents.

When hashes match

Two different inputs can produce the same hash. This is called a collision. Matching hashes are therefore not a mathematical guarantee of matching bytes.

Collisions exist because there are more possible inputs than 256-bit hashes. A secure cryptographic hash function, such as SHA-256, is designed to make finding them impractical. In practice, matching hashes are treated as strong evidence of matching bytes.

3. Which bytes does the reference correspond to?

A hash is a reference to the bytes used in the calculation. If the goal is to check an exact copy, preserving only the fields and values of a file is not enough.

Checking a test record

Consider a device that generates a JSON file containing a test result. Before being used as evidence in an audit, this file passes through an application that imports and re-exports its data.

The device calculates the SHA-256 of the original file before re-export. The auditor calculates the SHA-256 of the received version and compares the results. A new representation can preserve the fields and values and still produce a different hash because the bytes have changed. This checks whether the bytes have been preserved, not just the data read from them. It is an integrity check.

4. Preserving the reference

To detect changes from an earlier version, we need a preserved reference from that version. If someone replaces both the content and the stored hash, the comparison may show a match without revealing the substitution.

That is why it matters where the reference hash came from and how it was protected. The calculation alone does not identify who produced the content: anyone with the bytes can calculate the same hash.

5. A hash does not provide secrecy

A hash is not a reversible encoding like base64. There is no decoding operation that recovers the original content from it. This does not, however, prevent testing possible inputs.

If you know that a text is one of the two messages in the example, you can calculate both hashes and find out which one matches the observed hash. There is no need to reverse the calculation, only to compare results. Publishing a hash can therefore reveal information about predictable content.

What we learned

  • A hash is calculated from bytes. With the same input and the same algorithm, the result repeats.
  • Different hashes indicate different bytes. Matching hashes are strong evidence of equality, but collisions are possible.
  • An integrity check depends on knowing which bytes were used and preserving the reference.
  • A hash does not identify the author or protect predictable content from guessing attempts.
