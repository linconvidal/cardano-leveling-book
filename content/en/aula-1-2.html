Objectives

By the end of this lesson, you will be able to:

  1. separate the roles of networking, consensus and the ledger in a Cardano node;
  2. explain why serialization, inclusion and validation depend on the era's rules;
  3. identify which layer to investigate when a failure is observed.
Before you begin

Revisit Lesson 1.1 and the difference between transporting a proposal and accepting a transition.

Guiding question

Does receiving a transaction from another node mean it will be accepted?

1. Networking transports data

The networking layer maintains connections with other nodes, called peers, and diffuses blocks and transactions. Receiving a packet means only that the bytes arrived over a network path. Its structure still needs to be decoded, rules applied and a decision made about whether the object belongs in the chain or local state.

A transaction can reach the node and be rejected because it tries to spend an already used resource, offers an insufficient fee or lacks a required signature. A block can be received without belonging to the selected chain. Thus, “the node received it” and “the ledger accepted it” describe different events.

2. Consensus selects a history

Consensus organizes block production and chain selection. It handles competition between candidate histories and provides the rules by which participants converge. This layer does not decide whether an external report is true or interpret a transaction's business purpose.

A chain observed at a given moment can change near its tip. Applications need to distinguish receipt, observed inclusion and acceptance under their confirmation policy. The next chapter explores slots, epochs, stake and block production in more detail.

3. The ledger validates transitions

The ledger checks whether the operation can change the current state. Are the resources it intends to spend still available? Have the required authorizations been provided? Do the values and fee balance? These checks follow the era's rules and the current parameters. In the coming lessons, we will look at the fields that make these checks possible.

Indexers and explorers form another layer. They organize derived data for queries. A lagging indexer may omit a transaction already in the chain observed by a node; an interface may also truncate or translate values. A query failure should not automatically be attributed to consensus.

4. Eras and protocol evolution

Cardano evolves through eras. Each era introduces or changes capabilities, formats and rules. The hard fork combinator coordinates transitions between protocols within the same Cardano history. Tools need to know the active era and the applicable representation.

Being able to read a transaction's bytes is not enough to accept it. Its fields and effects must also comply with the era's ledger rules. Likewise, a library that recognizes a new field does not guarantee that the node, wallet and indexer in the environment offer the same support. In Lesson 1.6, we will see how fields are represented as bytes.

Verification context

When investigating a failure, record the network, era, node or library version and parameter source. These details allow the check to be repeated under the same conditions and help identify incompatibilities between tools.

Activity 1: identify the layer

Consider four observations: A receives a transaction from a peer; B rejects it because an input has already been spent; C cannot find it in its indexer; D observes a block that later leaves the selected chain. Classify each event.

Match each observation to the main area to investigate.

0 of 1 question answered.

Check answer

Receipt belongs to networking; the already spent input to the ledger; chain selection to consensus; the derived query to the indexer. This classification does not rule out combined causes, but it prevents transport, validity, selection and presentation from being treated as the same problem.

What we learned

  • The networking layer transports information between participants.
  • Consensus selects the chain the node follows; the ledger validates state transitions.
  • Validation rules depend on the era. Serializing a transaction is not enough to make it valid.
  • Indexers produce query views. A failure in such a view needs to be distinguished from a networking, consensus or validation failure.
