Objectives
  1. Distinguish the roles of the private key and the public key in a signature.
  2. Generate random bytes for study and explain why a predictable phrase cannot replace them.
  3. Recognize when a secret is exposed, even in another representation.
Before you begin

To follow this lesson, you need to recognize bytes and their hexadecimal representation and know that anyone with the same bytes can repeat a hash calculation.

Guiding question

How can we allow verification without sharing the ability to sign?

1. Verifying without receiving the secret

When receiving a message, a program may need to check its connection to a known key. A hash calculated only from the message does not establish that connection: anyone with the bytes can repeat the calculation.

A digital signature also depends on a secret. The challenge is to let others check it without giving them that secret and, with it, the ability to produce signatures.

A key pair separates these roles. The private key allows signing and must be protected. The public key, mathematically related to the private key, allows verification and can be shared. In a secure scheme, knowing the public key does not make it feasible to recover the private key or forge signatures.

2. Generating an unpredictable secret

A name, date or common phrase offers possibilities an attacker can test. Hashing this data does not remove its predictability: the attacker only needs to repeat the transformation for each guess. The length of the result alone does not indicate how difficult it is to guess its source.

Key generation uses a source of randomness suitable for security. The uncertainty about the generated value is described by entropy. In Python, the secrets module lets us obtain bytes from such a source.

Run the example to generate 32 bytes and view them in hexadecimal. The value is exposed in the output and may be saved in the browser: use it only for study, never as a secret in a real system.

import secrets

secret = secrets.token_bytes(32)

print(secret.hex())
print(len(secret), "bytes")

The call token_bytes(32) returns a bytes object. len(secret) reports its size, while hex() writes each byte as two characters. Run it again: you will see a new sample, also 32 bytes long. The appearance of the results does not prove the quality of the source; the choice of secrets is what matters here.

These bytes are material for studying secret generation, not a ready-to-use key for any algorithm. To generate a real key pair, a cryptographic library applies the procedures and formats of the chosen scheme.

3. The public part is not another representation of the secret

Obtaining the public key from the private material is a derivation defined by the scheme. Choosing two random numbers and calling one private and the other public is not enough: they must have the mathematical relationship that enables signing and verification.

This derivation is not a conversion to hexadecimal or base64 either. Those representations preserve the value and can be reversed. If someone receives the private key in hexadecimal, they have received the private key itself, not a public key.

The public key can be shared without granting the ability to sign, but its value alone does not tell us who it belongs to. To verify a signature from a specific person or device, we need to confirm that association, for example through a trusted registry or another established channel.

4. Protecting every copy

Consider an application that signs messages and records its operation in a log. This log may be sent to a support team. If it contains the private key, it will include a copy of the secret, even if access to the original key file is restricted.

The same care applies to configuration files, backups and conversations. Protecting storage and controlling who can access the private material are part of key custody. Investigating a verification failure requires the message, the signature and the public key used, not the private key.

5. The effect of an unauthorized copy

Suppose someone else copied the private key from a log. They can now produce signatures that will verify with the same public key as the sender’s. The calculation does not distinguish between two people using the same secret.

Deleting the log does not undo copies already obtained. The compromised pair must no longer be used; a replacement must be generated, and verifiers’ references must be updated through a trusted procedure. Signatures from the period of exposure also need to be investigated; the verification result alone does not reveal who produced them.

import secrets

Check answer

The size is information about the secret, not a representation of its value. The function that counts bytes gives us this quantity without converting or exposing the content. The output should show 32 bytes. Converting to base64 or omitting just a few characters does not meet the requirement to log only the size.

What we learned

  • The private key allows signing; the public key allows verification. The relationship between them is defined by the cryptographic scheme.
  • Secrets require unpredictable generation. A hash does not add the entropy missing from a common phrase.
  • Hexadecimal and base64 do not protect a private key. Logs, configuration files and backups can expose copies of it.
  • Verification does not identify who used a copy of the secret. The association between the public key and the sender, and key custody, each need their own safeguards.
