Guiding question

What does an address tell you about payment, stake and network, and what can you not conclude from it alone?

1. What lies behind an address

When preparing to receive funds, an application needs to specify where the value will go and under what condition it can be spent. On Cardano, the address carries information about this condition. It is not simply an account name or a private key to hand over to the payer.

The formats introduced with Shelley remain in use in later eras. CIP-19 describes their structure: a header identifies the type and network; the following bytes identify the credentials specified by that type.

A credential identifies a public key or a script through a hash. For a key, Cardano uses BLAKE2b-224 to produce this 28-byte hash. The private key remains outside the address.

2. Payment and stake have separate roles

The payment credential identifies the authorization needed to spend funds sent to the address. For a key credential, the transaction provides the corresponding public key and a valid signature. For a script credential, spending must satisfy the rule identified by that script.

The stake credential is involved in operations such as delegation to a stake pool and reward withdrawals. In current governance, it is also used to delegate voting power to a DRep. Controlling this credential does not grant the spending authorization of the payment credential.

A wallet normally manages both roles, but uses separate keys for them. A payment credential and a stake credential controlled by different parties can be combined. This separation allows a choice of who moves the funds and who manages the participation associated with stake.

One wallet, several addresses

Hierarchical wallets can derive several keys from the same recovery material, following a scheme such as CIP-1852. A wallet can therefore present several addresses rather than a single fixed identifier. It queries the ledger to find the funds associated with them.

The recovery phrase allows keys to be reconstructed in a compatible wallet. It is not a receiving address and must not be given to a dApp or to someone sending a payment.

3. Base, enterprise and reward

Let's compare three formats found in applications. They differ in the credentials they contain and the roles they serve.

Base: payment and stake

A base address combines a payment credential and a stake credential. It can receive funds and associate the ADA at that address with stake participation. Having both parts in the same address does not merge their authorizations.

Enterprise: payment only

An enterprise address has a payment credential without the stake part. It allows receiving and spending, but the ADA at that address is not associated with a stake credential for delegation.

Reward: reward account

A reward address, also called a stake address, identifies a reward account through its stake credential. It appears in operations such as withdrawing those rewards. It cannot be used as a transaction output destination to receive ADA or tokens. A withdrawal moves rewards from that account to a payment address.

What about script addresses?

Base and enterprise addresses can have a key or script payment credential. Thus, script address describes the authorization mechanism, not a fourth alternative to the three formats above. A stake credential can also be a script credential.

For example, an application can receive funds at an enterprise address whose payment credential is a script hash. To spend them, the transaction must satisfy that script; there is no private key for the script that can be recovered from a phrase.

4. Bech32 presents the bytes; the network provides context

What we copy from a wallet is usually a Bech32 encoding of the address. Like hexadecimal and base64, it writes bytes as text; it also includes a check that helps detect typing errors. The protocol works with the bytes, not with the text's appearance on screen.

The prefixes defined in CIP-5 help with interpretation:

  • addr1… and addr_test1… are used for mainnet and test payment addresses, respectively. Decoding confirms whether the format is base or enterprise.
  • stake1… and stake_test1… are used for mainnet and test reward addresses.

In the header, the network identifier is 1 for mainnet and 0 for testnets. Preprod and Preview use the same test identifier. An addr_test1… address therefore does not, on its own, tell you which of them to query.

The application needs to combine the address with the intended network and the corresponding access service. Switching networks in the wallet changes the environment being queried; it does not transfer funds between networks. A well-formed address also does not confirm the identity of the person who supplied it: check the complete destination with the expected source.

5. Inspecting and composing addresses

The PyCardano library lets you read an address's parts and compose other formats. The example uses a public base address from the CIP-19 test vectors. It then uses only its payment part to form an enterprise address and only its stake part to form a reward address.

from pycardano import Address

base_address = Address.from_primitive(
    "addr_test1qz2fxv2umyhttkxyxp8x0dlpdt3k6cwng5pxj3jhsydzer3n"
    "0d3vllmyqwsx5wktcd8cc3sq835lu7drv2xwl2wywfgs68faae"
)
enterprise_address = Address(base_address.payment_part, network=base_address.network)
reward_address = Address(staking_part=base_address.staking_part, network=base_address.network)

print("Network:", base_address.network.name)
print("Base:", len(bytes(base_address)), "bytes")
print("Enterprise:", len(bytes(enterprise_address)), "bytes")
print("Reward:", len(bytes(reward_address)), "bytes")

The output shows TESTNET and lengths of 57, 29 and 29 bytes. The credentials were reused, but the three addresses have different structures and roles. The code only composes addresses; it does not query the network or move funds.

What we learned

  • Payment and stake have distinct roles. Controlling one does not automatically grant control of the other.
  • Base combines payment and stake; enterprise has payment only; reward identifies the reward account.
  • A credential can identify a key or a script. Address format and authorization rule are related but different choices.
  • Bech32 presents the address bytes. The testnet identifier does not distinguish Preprod from Preview; the application also needs to know which network to access.
