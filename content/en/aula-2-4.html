Objectives
  1. Recover a predictable value by enumerating hashes.
  2. Build and verify a commitment with a private nonce.
  3. Distinguish limited disclosure, anonymity and controlled recovery of artifacts.
Before you begin

Review the Merkle proofs from Lesson 2.2 and the distinction between publications and files from Lesson 2.3. Use only the supplied fictional data. Do not put private documents, credentials or recovery phrases in the editors, which save drafts in this browser.

Guiding question

Can someone who sees a hash test what it hides?

1. Nine candidates are enough

A portal wants to publish a commitment to a result without revealing the result. The file is always the text status=...|revisao=..., encoded in UTF-8. There are three possible statuses and three revisions. An observer knows this format and the options, even though they have not received the file. The fixed data uses revisao for revision and aprovado, pendente and reprovado for passed, pending and failed.

SHA-256 produces the same digest for the same input. The observer does not need to reverse the algorithm: they can generate the nine candidate files and compare their hashes with the public value.

import hashlib
from itertools import product

def message(status, revision):
    return f"status={status}|revisao={revision}".encode("utf-8")

options = list(product(
    ["aprovado", "pendente", "reprovado"], ["R1", "R2", "R3"]))
published = hashlib.sha256(message("aprovado", "R2")).digest()
for status, revision in options:
    candidate = message(status, revision)
    if hashlib.sha256(candidate).digest() == published:
        print("found:", candidate.decode("utf-8"))
print("possible candidates:", len(options))

Change the actual status to pendente and run it again. The attack still works. Making the digest longer does not increase the number of possible messages. Sequential identifiers, nearby dates and files with few combinations can also allow guessing. A salt published alongside the digest can prevent the use of shared precomputed tables, but does not stop the observer from repeating this small search for each record.

2. Add a random secret to the commitment

To make the search harder, we will generate a private nonce: 16 fresh random bytes for each commitment, produced by secrets.token_bytes(16). An observer who does not receive the nonce no longer has only nine inputs to test. They must also discover a value chosen from 2 to the power of 128 possibilities.

The teaching profile guia.abertura.v1 calculates SHA-256(domain || nonce || length || data). The domain is the ASCII text GUIA-ABERTURA:v1 followed by a zero byte; the nonce is exactly 16 bytes; the length is an unsigned eight-byte integer, from most significant to least significant; and the data is the exact file bytes. The recipe fixes the boundaries to avoid ambiguous concatenations.

In the opening, the recipient receives the data and nonce through an authorized channel. They apply the same recipe and compare with the commitment obtained from the publication. The hash's resistance to finding alternative inputs supports its binding to those bytes. The nonce makes guessing the input before the opening harder; it does not encrypt the stored file.

import hashlib
import secrets

DOMAIN = b"GUIA-ABERTURA:v1\x00"
def commit(data, nonce):
    if len(nonce) != 16:
        raise ValueError("The nonce must be 16 bytes long.")
    input_bytes = DOMAIN + nonce + len(data).to_bytes(8, "big") + data
    return hashlib.sha256(input_bytes).digest()

data = b"status=aprovado|revisao=R2"
nonce = secrets.token_bytes(16)
published = commit(data, nonce)
print("correct opening:", commit(data, nonce) == published)
wrong_nonce = bytes([nonce[0] ^ 1]) + nonce[1:]
print("modified nonce:", commit(data, wrong_nonce) == published)

candidates = [f"status={s}|revisao={r}".encode("utf-8")
    for s in ["aprovado", "pendente", "reprovado"]
    for r in ["R1", "R2", "R3"]]
print("search with zero nonce:", any(
    commit(c, bytes(16)) == published for c in candidates))
# Leak simulation: the observer now knows the nonce.
print("with leaked nonce:", [c.decode("utf-8") for c in candidates
    if commit(c, nonce) == published])

The correct opening passes; changing one bit of the nonce fails. The search with a zero nonce should fail, except for the negligible probability that the randomly chosen nonce is exactly zero. This alone does not prove security: the difficulty comes from secret randomness, not just from changing the formula. The last line gives the nonce to the observer, and enumeration finds the file again.

Do not replace random generation with a date, counter or human password, or reuse a nonce across commitments. Preserving the nonce adds material that requires access control and backup. Losing the nonce prevents that commitment from being opened, even if the file still exists. A new nonce produces a different commitment and does not repair the old one.

3. The file stays outside the blockchain

Imagine someone needs to check the result published by the portal. The original file and nonce remain in the application's system. The blockchain receives the commitment and the name of the profile used to calculate it. Querying the transaction retrieves this reference, but does not recover the file or nonce: the verifier must receive them through another route.

In this example, publishing the commitment and profile name is enough. The portal remains responsible for storing the file and nonce, controlling who can receive them and maintaining a way to recover them. If an address must be published to locate the file, check what that address reveals: do not include people's names, internal paths or access tokens. The address helps locate the file; the commitment lets us check its bytes.

Commitments of this kind can also be placed in the leaves of a Merkle batch. The recipient receives the opening, position and proof, and compares the root with the publication. This requires its own profile, defining exactly how the commitment enters the leaf. Do not silently mix this variant with the file recipe from Lesson 2.2.

Activity: recover the correct opening

The application delivered a 16-byte nonce, but the verifier replaces it with zeros. Fix verify_opening to use the received nonce and compare the calculated digest with the expected commitment. Keep the calculation profile and test data. The fixed nonce below is public and for teaching purposes only; it offers no hiding. The fixed file text resultado da revisão means review result.

import hashlib

def commit(data, nonce):
    if len(nonce) != 16:
        raise ValueError("The nonce must be 16 bytes long.")
    return hashlib.sha256(b"GUIA-ABERTURA:v1\x00" + nonce
        + len(data).to_bytes(8, "big") + data).digest()

def verify_opening(expected, data, nonce):
    if len(nonce) != 16:
        return False
    return commit(data, bytes(16)) == expected

data = "resultado da revisão".encode("utf-8")
nonce = bytes.fromhex("00112233445566778899aabbccddeeff")
published = commit(data, nonce)
print("opening:", verify_opening(published, data, nonce))
print("another file:", verify_opening(published, data + b"!", nonce))
Check answer

The final check should be commit(data, nonce) == expected. The output now shows True and False. If the test with another file also passes, the verifier is not comparing the right bytes. If only the initial example passes, check whether you hard-coded its nonce instead of using the argument.

4. Limited disclosure is not anonymity

A Merkle proof reveals fewer files than the complete batch, but still exposes the opened item, its position and sibling hashes. If a sibling corresponds to a predictable leaf without a nonce, it too can be enumerated. Revealing less content does not automatically hide who published, who received or which publications are related.

A repeatedly used address, a stable identifier or coinciding times can link records. Even without names, additional information can allow reidentification. Pseudonymization preserves that possibility; assessing anonymization requires considering the context and reasonably available means. A hash, nonce or new address, on its own, does not justify calling data anonymous.

Public exposure is persistent. Removing a field from the portal does not remove copies of the history or material already delivered. Personal data and operational secrets should stay off-chain when they require access control or limited retention. If there is no need for a public commitment, keeping the record in a controlled system, or not collecting an unnecessary field, avoids this exposure.

5. Test recovery before relying on it

For the required retention period, preserve the exact file, the nonce, the profile and, if there is a batch, the data needed to recover the proof. Protect the copies and storage encryption keys. The period and access must match the purpose; do not keep everything indefinitely for convenience.

Run a restoration test with fictional data: recover the package through an authorized account, obtain the commitment through the defined query route and run verification. Then simulate a missing nonce and a missing sibling in the proof. The result should be “insufficient material”, not “false document”. Deleting the restricted material at the end of retention may end the ability to open the commitment; it does not erase the public commitment or revoke copies already shared.

What we learned

  • A small domain allows data to be discovered by comparing candidate hashes.
  • A random private nonce makes this search harder; opening the commitment requires preserving the bytes, nonce and recipe.
  • Limited disclosure reduces the content revealed, but does not eliminate correlation or guarantee anonymity.
  • Minimal publication depends on controlled recovery and an explicit retention decision.
