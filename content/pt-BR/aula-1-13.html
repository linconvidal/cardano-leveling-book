Objetivos
  1. Relacionar User Token e Reference NFT por policy ID, label CIP-67 e base name.
  2. Interpretar o wrapper do datum sem confundir versão do padrão com revisão do registro.
  3. Distinguir reference input de gasto normal e delimitar o que um validator confere.
Antes de começar

Retome identidade de ativos e CIP-25 na Aula 1.10 e a validação de sucessoras Plutus na Aula 1.12. Aqui aplicamos esses mecanismos a um estado descoberto por meio de um par de ativos.

Pergunta-guia

Como atualizar a descrição de um registro sem retirar do usuário o token que identifica esse registro?

1. Dois ativos com controles distintos

Considere o registro REC-0042. Seu usuário recebe um token que pode transferir. A aplicação precisa atualizar a descrição de referência de REC-0042 quando o relatório é revisado. Se o estado depender do output do usuário, cada atualização exigiria consumir esse output. A convenção CIP-68 separa o ativo transferível do ativo que identifica o estado de referência.

O User Token fica no output controlado pelo usuário. O Reference NFT identifica o output que carrega o datum de referência. Os dois pertencem à mesma policy e têm o mesmo nome-base, mas prefixos diferentes no asset name. São dois assets distintos; compartilhar policy não significa compartilhar condição de gasto.

Nesta aplicação, o User Token é um NFT com quantidade 1, em endereço de chave. O Reference NFT tem quantidade 1 e está em endereço de script Plutus, com um validator que limita atualizações. CIP-68 organiza representação e descoberta; a segurança da emissão, a unicidade do Reference NFT e as regras de gasto dependem das políticas e scripts escolhidos.

2. Os labels são bytes do asset name

CIP-67 define um prefixo de quatro bytes que codifica label e checksum. O Reference NFT usa label 100; o User Token usa 222 para NFT, 333 para token fungível (FT) ou 444 para Rich Fungible Token (RFT). Não escreva os dígitos “100” ou “222” como texto e não coloque o label apenas em metadata: o prefixo faz parte dos bytes do nome.

PapelLabelPrefixo CIP-67 em hex
Reference NFT100000643b0
User Token NFT222000de140
User Token FT3330014df10
User Token RFT444001bc280

O nome-base REC-0042 tem bytes UTF-8 5245432d30303432. Para a mesma policy, os nomes completos ficam:

base = "REC-0042".encode("utf-8")
usuario = bytes.fromhex("000de140") + base
referencia = bytes.fromhex("000643b0") + base
print("User Token:", usuario.hex())
print("Reference NFT:", referencia.hex())
print("nomes iguais?", usuario == referencia)
print("mesma base?", usuario[4:] == referencia[4:])

A saída tem nomes diferentes e bases iguais. O limite total de 32 bytes do asset name continua valendo, deixando no máximo 28 bytes para o nome-base. Em produção, valide o prefixo CIP-67, inclusive o checksum, com ferramenta compatível. Os prefixos completos da tabela bastam para reconhecer os três tipos usados no exercício.

Atividade 1: derive o nome da referência

Complete nome_referencia: receba os bytes do nome de um User Token, reconheça um dos três prefixos permitidos, conserve o nome-base e troque o prefixo pelo label 100. Rejeite com ValueError nomes menores que 4 ou maiores que 32 bytes e prefixos desconhecidos. A função não altera nem procura o policy ID; a consulta posterior deve manter a mesma policy.

def nome_referencia(nome_usuario):
    return nome_usuario

usuario = bytes.fromhex("000de1405245432d30303432")
print(nome_referencia(usuario).hex())
Conferir resposta

Depois de validar tamanho e os quatro bytes iniciais contra a tabela, devolva bytes.fromhex("000643b0") + nome_usuario[4:]. Para REC-0042, o resultado é 000643b05245432d30303432. Procurar esse nome sob outra policy pode encontrar um ativo sem relação com o usuário; o par é determinado pelos dois componentes.

3. O datum contém um wrapper, não apenas uma descrição

O output do Reference NFT guarda um inline datum segundo CIP-32. CIP-68 define um constructor 0 de Plutus Data com três campos: [metadata, version, extra]. A primeira posição é o mapa de metadata; a segunda é a versão de representação do padrão; a terceira contém Plutus Data adicional. Essa metadata em datum é visível a Plutus e não se confunde com transaction metadata dos auxiliary data.

Para o NFT de label 222 do exemplo, a metadata direta inclui name e image. Nossa aplicação acrescenta record_version e artifact_hash. O hash abaixo está abreviado e a notação utf8 apenas indica bytes de texto; este bloco não é CBOR serializado.

constructor 0 [
  {
    utf8("name"): utf8("Registro REC-0042"),
    utf8("image"): utf8("https://example.org/rec-0042.svg"),
    utf8("record_version"): 3,
    utf8("artifact_hash"): h'7c20...'
  },
  1,
  unit
]

A revisão do registro é 3; a versão do wrapper usada aqui é 1. Atualizar o relatório para revisão 4 não significa trocar automaticamente version para 4. O aplicativo deve interpretar a versão suportada antes de ler os demais campos. Dar ao campo da aplicação o nome record_version evita misturar esses contadores.

4. Ler por referência ou consumir para atualizar

Um reference input, definido na CIP-31, torna um output disponível para leitura sem consumi-lo. Seu valor não financia a transação, e só referenciá-lo não executa seu spending validator. Um script que lê essa referência precisa conferir a identidade completa do Reference NFT e o formato dos dados; não deve confiar em qualquer datum encontrado no mesmo endereço.

Para atualizar, a transação usa o output de referência como input normal, satisfaz seu spending validator e cria uma sucessora com o mesmo Reference NFT e datum atualizado. A regra deve conferir autorização, continuação do token e transição permitida, como no exercício Plutus. O User Token pode permanecer onde estava. Se outra transação já consumiu a referência, o builder precisa consultar o estado ativo e reconstruir sua tentativa.

A versão antiga continua no histórico, mas já não é um output disponível. Ler uma cópia em cache não demonstra que ela seja a versão atual; confira a referência e seu estado de consumo. Mudar código do validator continua exigindo a migração aceita pelo script anterior.

Atividade 2: o relatório mudou

REC-0042 passa de revisão 3 para 4. A versão CIP-68 continua compatível com 1. Uma aplicação propõe somente adicionar d42e8a1b6c90…#0 como reference input e alterar o datum em memória. Anote o que falta para efetivar a atualização.

Conferir resposta

Reference input apenas lê. A atualização precisa consumir d42e8a1b6c90…#0 como input normal e criar 0c7f92a6e4b1…#0 com o mesmo Reference NFT, sob a condição de gasto esperada, preservando o wrapper version 1 e alterando record_version para 4. O validator precisa aceitar essa transição. Alterar a memória da aplicação não altera o ledger.

5. O que a atualização não verifica

Mesmo um validator correto só verifica as condições implementadas sobre dados visíveis. CIP-68 não obriga o ledger a recuperar a imagem ou o relatório e não comprova sua correção. Para conferir artifact_hash, obtenha o original e use o mesmo algoritmo e a mesma representação de bytes definidos para o registro, como estudamos nas Aulas 0.1 e 0.2. Posse do User Token também não prova entrega do artefato, autorização institucional ou acesso ao repositório.

O par CIP-68 é útil quando a aplicação precisa dessa relação entre ativo transferível e estado descoberto por referência. Um estado de script sem token do usuário pode bastar em outro caso; adotar o padrão não elimina a necessidade de definir quem atualiza, como o estado é identificado e como os artefatos permanecem recuperáveis.

O que aprendemos

  • CIP-68 relaciona dois assets por policy e base name, com labels CIP-67 distintos.
  • O wrapper contém metadata, version e extra; revisão do registro é um campo separado.
  • Reference input lê sem gastar. Atualizar exige consumo e sucessora sob a regra aplicável.
  • O padrão organiza estado e descoberta, sem comprovar o conteúdo externo.
