--- title: Eventos, encadeamento e checkpoints map_title: Eventos e checkpoints summary: Encadear mudanças, detectar reescritas e acrescentar correções sem apagar o histórico. ---
Objetivos
  1. Construir três eventos ligados por hashes e localizar uma quebra.
  2. Comparar uma sequência com um checkpoint obtido por uma fonte independente.
  3. Acrescentar uma correção e distinguir o histórico da visão atual.
Antes de começar

Retome bytes e hashes no Módulo 0, metadata na Aula 1.9 e consulta de transações na Aula 1.11. Os exemplos usam somente Python disponível na apostila, sem wallet nem envio à rede.

Pergunta-guia

Se alguém consegue recalcular todos os hashes, o que impede que apresente uma história diferente?

1. O resultado mudou, mas a notificação já saiu

Um sistema acompanha o teste T-0142. Primeiro cria o registro como pendente. Depois registra o resultado aprovado. Por fim, registra que enviou uma notificação ao portal. A tela mostra apenas aprovado, mas essa palavra não explica como o registro chegou ali.

Um evento registra uma mudança ou ação declarada. A visão atual é calculada a partir dos eventos segundo uma regra da aplicação. Neste exemplo, criação, resultado e correção podem definir o resultado exibido; uma notificação não o altera. Os três eventos ficam em um arquivo externo. Não estamos criando três transações Cardano.

O campo seq determina a ordem de acréscimo. O campo prev contém o hash do evento anterior; o primeiro usa null. O hash de um evento inclui todos os seus campos, inclusive prev, mas não contém o próprio hash.

2. Experimento: quebrar e reescrever

Fixaremos uma receita local chamada guia.eventos.v1: JSON em UTF-8, chaves ASCII ordenadas, sem espaços opcionais, somente strings, inteiros e null usados neste exemplo, sem normalização Unicode. Antes dos bytes colocamos o prefixo ASCII GUIA-EVENTO:v1 e um byte zero. Calculamos SHA-256 sobre essa sequência. O prefixo identifica o uso e a versão.

Essa receita limitada torna a demonstração reproduzível; json.dumps com essas opções não implementa todo o JCS do RFC 8785. Uma integração precisa fixar um perfil interoperável e testar seus casos de borda, em vez de copiar o exemplo para qualquer JSON.

Execute. A primeira comparação aceita a cadeia. A segunda detecta a edição isolada. A terceira aceita os vínculos de uma reescrita inteira, mas a quarta rejeita sua cabeça contra o checkpoint guardado antes.

import hashlib
import json
from copy import deepcopy

def hash_evento(evento):
    dados = json.dumps(evento, sort_keys=True,
        ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(b"GUIA-EVENTO:v1\x00" + dados).hexdigest()

def anexar(cadeia, campos):
    evento = dict(campos, seq=len(cadeia) + 1,
        prev=hash_evento(cadeia[-1]) if cadeia else None)
    return cadeia + [evento]

def elos_conferem(cadeia):
    anterior = None
    for seq, evento in enumerate(cadeia, 1):
        if evento["seq"] != seq or evento["prev"] != anterior:
            return False
        anterior = hash_evento(evento)
    return True

cadeia = []
for campos in [
    {"tipo": "criado", "registro": "T-0142", "resultado": "pendente"},
    {"tipo": "resultado", "resultado": "aprovado"},
    {"tipo": "notificado", "canal": "portal"},
]:
    cadeia = anexar(cadeia, campos)
checkpoint = (len(cadeia), hash_evento(cadeia[-1]))
print("original:", elos_conferem(cadeia))

editada = deepcopy(cadeia)
editada[1]["resultado"] = "reprovado"
print("edição isolada:", elos_conferem(editada))
reescrita = []
for evento in editada:
    reescrita = anexar(reescrita, evento)
print("reescrita consistente:", elos_conferem(reescrita))
print("mesma cabeça:", hash_evento(reescrita[-1]) == checkpoint[1])

Mude também o resultado do primeiro evento e repita. O efeito se propaga pelos hashes posteriores. Remover o último evento, por outro lado, deixa os vínculos restantes consistentes: sem saber qual cabeça esperar, o verificador pode receber apenas um prefixo antigo.

3. O checkpoint fica fora da história apresentada

Um checkpoint associa uma posição a um hash de cabeça. No experimento, guardamos a dupla antes da edição. Num sistema real, ela precisa chegar por uma fonte que o apresentador da cadeia não possa substituir junto com os eventos: uma cópia previamente conferida, um checkpoint assinado por uma chave confiável ou uma publicação localizada na rede esperada.

Publicar a dupla em uma transação permite voltar ao compromisso observado. É preciso conferir o publicador esperado e a inclusão; aceitar qualquer transação com outro hash permitiria trocar a referência. A rede preserva a publicação, mas não avalia o resultado do teste.

Um checkpoint de três eventos compromete aquele prefixo. Uma cadeia com quatro eventos pode preservá-lo. Isso não demonstra que o quarto é o mais recente, que nenhum evento deixou de ser capturado ou que todos os resultados são corretos. Para avaliar atualidade, obtenha também a cabeça mais recente pela rota definida para o registro.

4. Corrigir por acréscimo

A revisão do arquivo de origem revela que o resultado deveria ser reprovado. O sistema acrescenta o evento 4 com tipo correcao, resultado reprovado, motivo e dois vínculos diferentes: prev aponta para o evento 3, enquanto alvo aponta para o hash do evento 2. O primeiro continua a cadeia; o segundo identifica a declaração corrigida.

A visão passa a mostrar reprovado e deve permitir abrir a correção. O histórico ainda mostra que houve um resultado aprovado e uma notificação. Acrescentar uma correção não desfaz a notificação nem elimina a necessidade de avisar seu destinatário.

Se a correção declara ocorrido_em = 2026-09-10T10:00:00Z e seu checkpoint foi observado às 11:30, esses horários descrevem coisas diferentes. O primeiro foi declarado pelo emissor; o segundo registra a consulta da publicação. Bloco e slot localizam a inclusão. Nenhum deles comprova que o teste ocorreu às 10:00. Não reordene a cadeia pelo horário declarado para “consertar” essa diferença.

Atividade: aceite a correção, rejeite a reescrita

O verificador abaixo já confere os elos, mas esquece o checkpoint e termina com True. Repare sua conclusão: rejeite uma cadeia menor que quantidade e compare o hash na posição comprometida com cabeca. Não exija que a cadeia termine nessa posição, pois correções podem ter sido acrescentadas. O contrato recebe checkpoints com quantidade positiva.

import hashlib
import json

def hash_evento(evento):
    dados = json.dumps(evento, sort_keys=True,
        ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    return hashlib.sha256(b"GUIA-EVENTO:v1\x00" + dados).hexdigest()

def anexar(cadeia, campos):
    return cadeia + [dict(campos, seq=len(cadeia) + 1,
        prev=hash_evento(cadeia[-1]) if cadeia else None)]

def verificar(cadeia, quantidade, cabeca):
    anterior = None
    for seq, evento in enumerate(cadeia, 1):
        if evento["seq"] != seq or evento["prev"] != anterior:
            return False
        anterior = hash_evento(evento)
    return True

cadeia = []
for tipo in ["criado", "resultado", "notificado"]:
    cadeia = anexar(cadeia, {"tipo": tipo})
cabeca = hash_evento(cadeia[-1])
corrigida = anexar(cadeia, {
    "tipo": "correcao", "alvo": hash_evento(cadeia[1]),
    "resultado": "reprovado", "motivo": "erro de leitura",
})
print("prefixo preservado:", verificar(corrigida, 3, cabeca))
print("cauda omitida:", verificar(cadeia[:2], 3, cabeca))
Conferir resposta

Antes da comparação, teste len(cadeia) < quantidade e retorne False nesse caso. Caso contrário, a conclusão é hash_evento(cadeia[quantidade - 1]) == cabeca. A subtração converte a posição contada a partir de 1 em índice Python. A saída correta é True para a correção acrescentada e False para a cauda omitida.

Comparar apenas o último hash rejeitaria uma extensão legítima. Aceitar apenas os elos permitiria a reescrita consistente. Precisamos das duas conferências.

O que aprendemos

  • A visão atual aplica regras aos eventos; ela não substitui o histórico.
  • Elos detectam inconsistências locais. Um checkpoint independente permite comparar a história com um prefixo conhecido.
  • Uma correção aponta para a cabeça anterior e identifica separadamente o evento corrigido.
  • Horário declarado, inclusão e observação da publicação não são o mesmo instante.
